# 강태산 대리 · 카카오톡 업무 에이전트 개발 서버

카카오 스킬 요청을 받으면 직원 계정을 확인하고, 자연어를 모델에 넘겨 필요한 업무를 고른다. Python이 허용된 업무의 입력을 검증하고 실제 도구를 호출한다. 실행 결과는 SQLite에 저장된다. 메뉴는 진입점이며 정해진 문구를 입력할 필요는 없다.

## 실행

Python 3.12 환경에서 의존성을 설치한 후 실행한다.

```powershell
python -m pip install -r requirements.txt
python agent.py
```

| 환경 변수 | 설정 |
|---|---|
| OPENAI_API_KEY / TAESAN_MODEL | 서버에 보관하는 OpenAI API 자격증명 / 사용할 모델 |
| TAESAN_WEBHOOK_SECRET | 32자 이상 난수. 카카오 스킬 URL의 끝 경로에 사용 |
| TAESAN_STAFF_IDS / TAESAN_ADMIN_IDS | 승인된 카카오 스킬 사용자 식별자 목록. 쉼표 구분 |
| TAESAN_SHEET_ID | 우선 테스트 사본의 스프레드시트 ID |
| TAESAN_DELIVERY_READ_SHEET_ID | 배송 건수 전용 읽기 파일 ID. 미설정 시 액자화환 주문 통합관리 운영 파일을 읽습니다. 사본을 쓰는 환경에서는 사본 ID를 지정합니다. |
| TAESAN_GOOGLE_CREDENTIALS | 필요할 때 Google 서비스 계정 자격증명 파일 경로. 관리형 환경에서는 기본 자격증명 사용 가능 |
| TAESAN_SCROLL_DIR / TAESAN_SCROLL_PYTHON | 기존 자동족자와 연결 모듈이 설치된 폴더 / 해당 Python 실행 파일 |
| TAESAN_PUBLIC_URL | 카카오에서 접근 가능한 HTTPS 서버 주소. 서류 링크 생성에 사용 |
| TAESAN_DATA | 영구 저장 경로. SQLite와 처리 이력을 저장 |
| TAESAN_STOCK_WRITERS / TAESAN_LIVE_WRITE / TAESAN_STOCK_TAB_ID | 등록 허용 직원 / 쓰기 활성화 값 1 / 대상 재고 탭의 숫자 ID. 기본값은 쓰기 비활성 |
| KAKAO_REST_API_KEY | 배송비DB에 확인된 좌표가 없는 배송지의 카카오 지도 주소 검색에 사용 |

카카오 스킬 URL은 `https://서버주소/skill/난수`다. HTTPS 프록시가 POST와 파일 GET만 전달하도록 구성한다. 기존 자동족자 8768 포트는 로컬에서 유지한다. 직원 식별자는 관리자와 통제된 테스트 대화로 확인한 값으로 등록한다. 카카오 화면에 결과가 늦게 나오는 요청은 접수번호와 결과 보기 버튼을 반환한다. 결과 링크는 5분 후 만료하며, 결과 보기에서 다시 발급할 수 있다.

## 현재 동작

### 카카오 배송루트

승인된 직원이 `배송루트`를 누르거나 `다음 주 토요일 구로 배송루트 짜줘`라고 말하면 배송관리와 배송원DB를 읽고 서버에서 배정안을 계산한다. `10km 이내는 2시간으로 바꿔`, `이동시간 10분 추가`, `김석헌 빼고 다시 짜줘`, `13358번 이동시간 45분으로`, `다시 계산`처럼 직전 배송일과 조건을 이어갈 수 있다. 조건은 계정별로 24시간 보관하며 `조건 초기화`로 기본값을 복원한다. 배송일을 바꾸면 주문별 제외와 이동시간을 초기화한다.

구로센터 출고의 미배정 주문이 대상이다. 배송원이 이미 담당 중인 건은 다른 센터 일정도 포함해 해당 날짜의 신규 배정에서 그 배송원을 제외한다. 시트에서 확정 동선의 상세 시간은 읽을 수 없으므로 기존 일정 사이에 주문을 삽입하는 기능에는 확정 배송루트 연결이 필요하다. 결과의 설치시간은 거리 기반 추정이며 배정안 작성 단계에서 운영 데이터를 변경하지 않는다.

카톡에는 날짜별 배정 요약 이미지와 `엑셀 내려받기` 버튼을 보낸다. 엑셀에는 배송원별 방문 순서, 행사시간, 설치 완료 예상시간, 배송장소, 운반 수량과 미배정 사유를 담는다. 파일 주소는 1시간 동안 열리며, 주소를 전달하면 받은 사람도 유효기간 동안 열 수 있다. 만료 후 `최근 배송보고서`라고 말하면 본인이 만든 최근 보고서에 새 주소를 발급한다.

승인된 직원이 `내 메뉴에 최근 배송보고서 버튼 추가해줘` 또는 `내 메뉴에서 최근 배송보고서 버튼 빼줘`라고 요청하면 자기 메뉴만 즉시 바뀐다. 프로그램 코드와 운영 시트 변경 요청은 기존 승인 흐름을 사용한다.

### Render 무료 테스트 배포

이 디렉터리의 소스와 `render.yaml`을 비공개 Git 저장소의 루트에 올리고, Render에서 저장소를 연결해 Blueprint를 생성합니다. `OPENAI_API_KEY`와 `TAESAN_MODEL`은 Render 화면에서 입력합니다. 서비스 기동은 `/healthz`에서 확인합니다. 시트 연결 및 운영 쓰기는 첫 배포 이후에 설정합니다. Free 인스턴스의 SQLite는 재시작과 재배포 시 초기화될 수 있으므로 실제 직원 등록과 업무 이력 보관에 사용하지 않습니다.

- 오늘 배송관리, 센터 재고 조회. 재고 입고는 해당 직원 권한과 쓰기 설정을 모두 확인한다. 확인되지 않은 쓰기는 중복 방지를 위해 자동 재시도하지 않는다.
- 맞춤 족자 제작과 번호를 지정한 재제작. 기존 공장 PC 렌더러로 넘기고, 원래 주문의 나머지 족자 결과를 함께 보존한다.
- 시트 구조 변경 문의는 요약해 승인 대기함에 접수한다. 대표 계정이 `승인 대기`라고 입력하면 확인할 수 있다. 서버는 시트 구조 변경 명령을 실행하지 않는다.
- 사진 첨부 수신, 대표 휴대폰 선제 알림과 승인 실행, 인수증 이미지, 공장 출력, 주문·정산·마케팅 확장 기능은 별도 연결이 필요하다. 결과 링크를 켜기 전 사내 HTTPS 접근 방식과 테스트 채널에서의 표시를 확인한다.

첫 반영 순서: 인증된 대표 계정 → 읽기 전용 테스트 사본 → 사본 재고 입고 → 공장 PC 족자 PNG/PDF → 개발 채널 스킬 연결. 운영 원장 쓰기는 사본에서 열 위치와 날짜 서식을 확인한 뒤 켠다.

## 직원·대표 등록과 승인

서버와 같은 `TAESAN_DATA`를 지정한 환경에서 `python agent.py --issue-code admin`으로 대표용 등록 문장을 발급한다. 대표 코드는 15분 동안 한 번만 쓸 수 있으며 대표에게만 전달한다.

대표가 카톡에서 기능 개발을 요청하면 개발 목록에 바로 등록합니다. 직원 요청은 대표가 `개발 요청 보여줘`로 열고 `승인`이라고 보내면 등록합니다. 여러 건이면 먼저 요청 제목을 누릅니다. 정기 개발 작업에서 승인된 요청을 읽고 검증용 변경안을 남깁니다. 요청자는 카톡에서 `내 개발 요청 상태`로 승인 대기, 작업 대기, 검증 완료를 확인할 수 있습니다. 운영 반영은 별도 배포 작업에서 확인합니다.

배송 건수는 날짜를 생략하면 오늘, 센터를 생략하면 전체 센터를 조회합니다. `오늘 배송 몇 건?`은 미완료, `배송완료 체크된 건 몇 개야?`는 완료, `오늘 전체 배송 몇 건?`은 원장 전체 건수를 보여줍니다. 원장과 배송관리에서 주문번호·배송일을 대조할 수 없으면 그 주문은 상태 확인이 필요한 건으로 표시합니다.

시트 구조 변경은 기존 `승인 대기`에서 확인·승인합니다. 구조 변경 승인은 개발 목록으로 전송하지 않습니다.

## 검색 제한과 직원 첫 입장

채널 검색을 끄고 직원에게 링크를 공유한다. 신규 직원은 처음 한 번 “직원 신청 이름”을 보낸다. 대표가 “직원 승인 대기”에서 대상과 권한을 승인하면, 이후 비밀번호나 코드 없이 사용한다. 일반 권한은 조회·제작, 입고 포함 권한은 재고 쓰기 활성화 시 입고까지다. 직원의 등록 이름은 본인 주장으로만 표시하므로 대표가 실제 직원을 확인한다.

배송원 변경과 택배 일괄 완료는 이 빌드의 실행 대상에 아직 포함되지 않는다. 설치 시 운영 상태를 먼저 확인하고 기존 스크립트의 상태 DB와 동기화 경로를 사용한다.

## 카톡 간편 초대장

승인 직원은 메뉴의 `초대장`을 누른 뒤 원본 주소 한 개 또는 행사명·일시·장소가 적힌 안내를 보냅니다. 행사나 예식별 주문 주소는 블로그페이에서 93,500원과 99,000원 상품을 조회해 연결합니다. 기존 청첩장 주문 내역과 PayApp 전용 주문서는 아래 기존 경로에서 계속 관리합니다.

- `BLOGPAY_SHOP_ID`, `BLOGPAY_API_TOKEN`으로 운영 상점의 상품 목록을 조회합니다. `BLOGPAY_INVITATION_TEMPLATE_ID`에 검증한 비진열 원본 상품 번호를 설정하고 `BLOGPAY_INVITATION_AUTO_CREATE=1`로 켜면 빠진 상품을 복제합니다.
- 자동 복제에는 영구 저장소에 연결된 `TAESAN_DATA`가 필요합니다. 복제 저장 응답이 없으면 상품 목록을 조회합니다. 복제 결과가 모호하면 관리자가 확인할 때까지 신규 복제를 보류합니다.
- 원본을 자동으로 읽을 행사 사이트는 `INVITATION_PUBLIC_HOSTS`에 호스트 이름을 쉼표로 구분해 추가할 수 있습니다. 신규 사이트는 공개 HTML과 구조화 행사 데이터가 제공되는지 확인합니다.
- 새 간편 초대장과 썸네일의 공유 기한은 행사일 다음 달 같은 날짜까지입니다. 해당 날짜가 없으면 다음 달 말일까지입니다.

## 초대장 전용 주문서

1. 블로그페이에서 기존 쌀빛그림화환 상품을 복사해 새 예식 상품 두 개를 등록합니다. 태산이가 안내한 상품명을 사용하고 가격을 각각 93,500원과 99,000원으로 설정합니다. 메인진열은 끄고 주문 가능한 판매 상태로 둡니다.
2. 태산이에서 `초대장`을 선택해 새 청첩장 링크를 보냅니다. 행사 주소를 읽지 못하면 도로명 또는 지번 주소를 답장합니다. 태산이가 각 복사본의 사진, 옵션과 가격을 읽어 예식별 주문서를 만듭니다.
3. 대표는 태산이에서 `초대장 주문 내역`으로 결제 완료와 취소 주문을 확인합니다. 주문은 `TAESAN_DATA`에 저장됩니다. 블로그페이 주문 목록에는 추가되지 않습니다.

전용 주문서 사용에는 `INVITATION_CHECKOUT_ENABLED=1`, `TAESAN_PUBLIC_URL`과 페이앱 판매점의 `INVITATION_PAYAPP_USER_ID`, `INVITATION_PAYAPP_LINK_KEY`, `INVITATION_PAYAPP_LINK_VALUE`, `INVITATION_PAYAPP_REQUEST_KEY`가 필요합니다. 값을 등록하고 실제 사용 가능한 결제수단, 결제 완료 통보, 취소를 검증한 뒤 초대장 링크를 고객에게 공유합니다. 결제수단은 페이앱 가맹점 설정을 따릅니다. 전용 주문서 사용 설정을 끈 상태에서 생성한 초대장은 기존 블로그페이 주문서에 연결됩니다.


## 벨라비타 쇼핑몰 관리

대표 계정에서 태산이에게 `쇼핑몰 관리`를 입력하면 10분 동안 유효한 관리
링크가 나옵니다. 상품을 등록하고 행사 이름, 일시, 홀, 설치 주소를 입력하세요.
판매가에 `93500,99000`을 입력하면 가격별 주문서가 생깁니다. 상품 수정은
이후에 발급하는 링크부터 적용됩니다. 발급된 링크는 개별로 판매를 중지하거나
재개할 수 있습니다. 결제·취소는 같은 관리 화면에서 확인합니다.

기존 페이앱 환경 변수와 `TAESAN_PUBLIC_URL`을 사용합니다. 새 주문서의 실제
결제는 `SHOP_CHECKOUT_ENABLED=1`로 별도로 활성화합니다. 테스트에서는 이
값을 비워두면 상품과 링크 발급, 주문서 열기까지 확인할 수 있습니다.

상품·판매 링크·주문은 기존 SQLite에 보관됩니다. 단일 인스턴스에서
`TAESAN_DATA`를 실제 영구 디스크 마운트 아래로 설정하고 재배포 뒤 보존을
확인한 후 실결제를 사용하세요. 기존 데이터를 사용 중이라면 빈 디렉터리로
환경 변수만 변경하지 말고 기존 DB 및 초대장 파일을 먼저 백업하고 이전하세요.
페이앱 요청이 중간에 끊긴 주문은 관리 화면에 확인 필요로 표시됩니다.

부분취소 거래별 금액과 합계, 원결제금액, 페이앱 통보 이력을 함께 확인할 수 있습니다.
확인 필요 주문은 페이앱 원거래를 대조해 관리 화면에 기록하고 통보 재전송으로 확정합니다.
대조 기록만으로 결제 완료 처리하거나 결제를 자동 재요청하지 않습니다.
백업·복구, 독립 HTTPS 테스트와 실가맹점 검증 절차는
[쇼핑몰 운영 절차](docs/shop-operations.md)를 참고하세요.

결제 확인 주문은 직원·주문자에게 입력 문구 샘플을 첨부한 MMS 알림을 등록합니다.

## 카톡 주문 등록과 직원 주문관리

- 승인된 직원이 `주문 접수`와 함께 주문 내용을 전달하거나 지원되는 청첩장·부고장 주소와 보내는 분을 보내면 접수한다. `TAESAN_ORDER_SHEET_ID`를 연결하면 실제 드롭다운과 배송채널을 대조해 확인된 값만 쓴다. 부고장의 입관·발인은 비고에 넣고 배송일시가 없으면 주문서 보고에 `확인 필요`로 표시한다.
- 첫 검증에는 별도 테스트 사본의 ID를 사용한다. 기존 시트의 드롭다운과 수식은 수정하지 않는다. 이 서버에서 시작한 주문은 AC열의 주문 식별자로 재조회한다. 기존 Apps Script와 같은 원장에 동시에 쓰는 경우를 검증하기 전에는 운영 원장 쓰기를 켜지 않는다.
- `초대장 주문관리` 버튼은 승인 직원에게 일회용 로그인 주소를 준다. 이 화면에는 전용 주문서의 페이앱 주문만 표시한다. 수정은 원장에 연결된 주문을 대상으로 다시 시도할 수 있고, 변경 전후 값과 작업자를 기록한다.
- 구로 직원 문자에는 `SOLAPI_API_KEY`, `SOLAPI_API_SECRET`, `SOLAPI_FROM`과 대표 계정의 `직원 알림 설정 신청번호 구로 휴대폰번호` 등록이 필요하다. 수원 직원은 해당 문자 대상에 포함되지 않는다. 문자 접수 응답이 불명확한 건은 발송사 기록을 확인하기 전까지 재전송하지 않는다.
