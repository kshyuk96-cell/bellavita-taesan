# 희망일출·벨라비타 공통 쇼핑몰/ERP 업무 묶음

## 개발 후보의 위치

PR #56 공통 코어 후보 `d490598`에서 분기한 후속 개발 묶음이다. 두 회사 이름은 대표가 지정했으며 `Companies.planned()`에 등록한다. 실제 쇼핑몰 계정·상품·판매/취소 규칙은 미연결/미확정이므로 회사 설정과 상태 매핑의 기본값은 비활성화다. 테스트에서만 가상 설정을 활성화한다. 벨라비타 ERP 개발 완료 전에도 코어를 준비하기 위한 작업이며, 이 라이브러리 자체가 쇼핑몰이나 ERP의 인증·결제 API는 아니다.

최신 main 확인 기준 `db742efa7ec7291293659e02dd1e50aa26a1465c` (#54 ERP 게이트웨이, #55 초대장 상품 검증 보존). main 병합·운영 배포·시트 쓰기·실제 결제·발송·예약 변경 없음.

## 승인된 10개와 연결 계약

| 항목 | 구현 | 실제 연결 시 필요한 사항 |
|---|---|---|
| 1 회사별 설정 | `commerce.Companies`, `Company` | 희망일출/벨라비타의 검증된 필수값·통화·운영 규칙. 회사는 로그인 세션에서 결정 |
| 2 공통 주문 | `commerce.normalize_order`, `Order` | 쇼핑몰별 명시 필드 매핑, 출처·외부 ID·현재 버전·생성 세대 |
| 3 상품·옵션 | `catalog.Catalog.quote` | 실제 가격·판매/비전시 상태·옵션·재고를 읽는 제공자 및 조회 영수증 |
| 4 같은 주문 초안 | `order_drafts.Drafts` | 직원별 초안 ID·예상 수정 번호, 필수값 부족 목록, TTL 정리 |
| 5 실제 장소 중복 | `order_duplicates.DuplicateReviewer` | 현재 후보 주문의 실제 조회, 보내는 분 DB 키, 도로명/지번을 같은 건물 ID로 확인하는 주소 제공자 |
| 6 상태 변환 | `order_workflow.StatusMap` | 회사·출처별 결제/제작/배송/취소 매핑과 확인된 충돌 조합 |
| 7 변경·취소 판단 | `RequestPolicy`, `assess_request` | 실제 회사 정책, 현재 주문/버전/생성 세대에 묶인 모든 상태. 가능 판정도 실행 승인이 아님 |
| 8 제작·배송 인계 | `handoff` | 실제 업무별 필수값, 원본 참조, 현재 버전. 결과는 검토 초안이며 제작/배송 실행 없음 |
| 9 중복·역순 알림 | `Webhooks` | 정확한 payload의 서명/계정/재전송 유효기간을 검증하는 제공자, 신뢰할 수 있는 주문별 순번 |
| 10 회사별 평가 | `company_evaluation.run_fixture_evaluation` | 지금은 가상 업무 계약만 실행. 실제 모델/직원/쇼핑몰·ERP 시험은 별도 |

## 중요한 구별

- `Order.version`은 현재 변경 버전이고 `Order.generation`은 같은 행/주문번호를 재사용해도 달라지는 최초 생성 세대다. 형님·직원은 계속 행 번호로 사용해도 된다. 연결 프로그램이 두 값을 내부에서 관리해야 한다. 콜백 등록은 생성 세대가 없으면 거부한다. 직원에게 세대 ID를 입력시키지 않는다.
- 행사시간과 배송 요청 시각은 독립 값이다. 한쪽이 없으면 다른 쪽을 복사하지 않는다. 보내는 분 DB 키는 호스트의 확인된 조회에서 넣어야 하며 고객 문장·모델이 임의 생성하지 않는다.
- 주문 초안은 원장을 바꾸지 않는다. 변경/취소의 `eligible`도 `can_execute=False`, `approval_required=True`다. 실제 반영에는 #56의 스냅샷 승인·권한 검사와 제공자의 원자 버전 비교/반영 후 재조회가 필요하다.
- 상태 관측은 회사·출처·주문·버전·생성 세대가 모두 일치해야 요청 판단에 사용한다. 일부 상태가 없거나 결제/배송이 불명확하면 검토 필요다. 배송 알림이 왔다고 결제 완료로 추정하지 않는다.
- 중복 결과 `clear`는 전달된 후보 범위 안에서 의심 건이 없다는 뜻이다. 후보 조회 실패를 빈 배열로 바꾸면 안 된다. 후보 조회 근거는 호스트가 별도로 검증한다. 주소 해석이 실패/다중 일치/불명확이면 `review`, 같은 건물의 층/홀/본관·별관 차이는 구분한다. 근접 좌표나 유사한 건물명만으로 확정하지 않는다. DB 키가 없으면 보내는 분 이름만으로 확정하지 않는다. 결과는 주문 참조·사유만 반환하고 자동 삭제/취소/경고 발송은 하지 않는다.
- 콜백은 로컬 통합 상태 관측표만 갱신하며 운영 원장/결제 상태를 직접 바꾸지 않는다. 서명을 검증한 신뢰 제공자가 정확한 회사·출처·주문 세대·순번을 전달해야 한다. 서명 원문과 공식 API 응답에서 표준 payload로 변환하는 호스트 코드는 연결 시 구현한다.
- 새 순번의 미등록/충돌 알림은 관측 순번을 남기고 검토 상태로 막는다. 더 오래된 알림은 무시하며 다음 부분 알림으로 검토 상태를 자동 해제하지 않는다. 현재 묶음에는 검토 해제 API가 없다. 실제 제공자의 전체 상태를 대조하는 관리자 복구 흐름을 연결하기 전에는 운영 자동 동기화를 켜면 안 된다. 신뢰할 순번이 없는 제공자는 단순 도착 시각으로 대체하지 않고 별도의 공식 상태 재조회 어댑터가 필요하다.
- 초안의 민감 필드는 기본 30분 유효하며 `Drafts.purge()`를 호출해 정리한다. 콜백 영수증은 중복/역순 방지를 위해 유지하고 상태값·식별자·해시만 저장하며 고객 원문이나 서명을 저장하지 않는다. 영구 디스크·백업·복구·운영 보존 정책은 연결 시 결정한다.

## 가상 평가와 점수

`docs/taesan-company-evaluation.json`은 `run_fixture_evaluation('hope-sunrise'|'bellavita')`의 재현 가능한 결과다. 각 회사 100개(형식 해석·업무 판단 규칙·초안 실행 제어·근거 구분 각 25개), 총 200개가 관측되어 통과했다. 외부 모델을 호출하지 않고 가상 주문/카탈로그/임시 SQLite를 사용한다.

이는 업무 규칙 테스트 통과율이며 AI 이해력 100점 또는 운영 목표 90점 달성을 뜻하지 않는다. `measurement=business_contract_scenarios`, `model_called=False`, `operational_connection=False`, `operational_score_verified=False`로 명시한다. 기존 운영 기준 이해/판단 62.5, 개발 75는 실사용 관측 전 유지한다. 연결 후 실제 모델·두 회사의 직원 권한·카카오/ERP/쇼핑몰 경로를 별도 평가한다.

## 재현

Python 3.12, 신규 업무 시험 135개 + 이전 공통 코어 104개 + 기존 운영 회귀 51개, 총 290개 통과. 회사별 가상 200개 시나리오는 평가 시험에서 별도로 실행한다.

```sh
python -m unittest discover -s taesan_core/tests -t . -v
python -m unittest discover -s tests -q
git diff --check
```

전체 회귀는 전용 임시 TAESAN_DATA, 가상 계정/스킬 비밀값, 모의 제공자로 실행한다. 운영 자격증명을 주입하지 않는다. 연결 제공자 기본 비활성화를 유지한다. PR #56의 기존 공통 코어 및 원래 운영 테스트도 함께 실행한다.
