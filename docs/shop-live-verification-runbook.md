# 첫 운영판 실제 연동 검증 절차

2026-11-14 한국 시간 기준. 상품 조건은 운영자 승인 완료이며 디자인은 추후 변경한다. 현재 독립 검증 서버는 모의 전용이다. 이 문서는 실제 계정 연결 후 사용할 절차이며 실행 완료 기록이 아니다.

## 1. 기존 운영 데이터와 시험 환경 구분

기존 Render main 서비스는 변경하지 않는다. Environment에서 `TAESAN_DATA` 항목만 확인한다. 없으면 미설정으로 기록하고, 기본 경로를 영구 디스크 경로라고 가정하지 않는다. `/var/data` 디스크 부착만으로 DB 보존을 판정하지 않는다.

셸 접근이 확보되면 앱을 시작하지 않고 기존 경로와 `state.sqlite3` 존재 여부를 읽기 전용으로 확인한다. [저장소 점검 도구](../tools/check_shop_storage.py)는 명시한 기존 DB만 읽는다. 현재 main에 도구가 없다고 운영 배포하지 않는다. 도구를 검토한 뒤 임시 파일로 실행하거나 표준입력 실행 방식을 사용한다. 이후 기존 DB·초대장·샘플 파일 백업과 새 경로 복구를 확인한다. 새 DB 생성이나 경로 이동으로 점검을 대신하지 않는다.

실가맹점 시험은 별도로 승인된 독립 환경에서만 한다. 현재 `/verification` 모의 서버에 운영 키를 복사하지 않는다. 운영 주문·원장·직원 알림과 혼합하지 않는다. 아직 그 실가맹점 환경을 만들거나 실거래를 실행한 것은 아니다.

## 2. 페이앱 가맹점과 거래 대조

사업자 가입은 운영자가 확인했다. 판매자 설정에서 API 권한과 `INVITATION_PAYAPP_USER_ID`, `INVITATION_PAYAPP_LINK_KEY`, `INVITATION_PAYAPP_LINK_VALUE`, `INVITATION_PAYAPP_REQUEST_KEY`에 대응하는 항목을 비공개로 확인한다. 값은 채팅·저장소·스크린샷에 노출하지 않는다.

가맹점 제공 시험 수단·허용 금액·취소 권한을 확인한다. 실거래가 필요하면 실행 전 금액·수단·취소 계획에 대한 별도 승인을 받는다. 공식 문서의 최소 결제요청 금액은 1,000원이지만, 이 사실만으로 시험 금액이나 거래가 승인된 것은 아니다.

통보 주소는 해당 시험 환경의 HTTPS `/invitation-orders/payapp`이다. 기존 운영 통보 주소를 바꾸지 않는다. 고유 주문번호·서버 계산 금액·페이앱 결제번호를 함께 기록한다.

| 항목 | 대조 기준 |
|---|---|
| 승인 | `pay_state=4`, 서버 금액 및 결제번호 일치 |
| 요청취소 | `8/32`; 이미 승인된 거래를 취소 완료로 덮어쓰지 않음 |
| 승인취소 | `9/64`; 늦은 승인 통보로 되돌리지 않음 |
| 부분취소 | `70/71`, `orig_mul_no`·`orig_price`와 개별 취소번호·취소액 대조 |
| 중복 통보 | 동일 취소번호의 70/71을 한 번만 합산 |
| 결과 불명 | 판매자 거래내역과 먼저 대조, 새 결제 자동 요청 금지 |
| 응답 | 인증·금액 검증 후 `SUCCESS`; 단순 성공 화면으로 승인 판정하지 않음 |

중복·역순 통보를 검증하려고 운영 결제 통보를 임의로 조작하지 않는다. 합성 통보는 격리된 모의 데이터에서만 실행한다. 실제 환경에서는 공급사가 허용한 재통보 수단과 거래 내역을 사용한다.

## 3. 직원·고객 카톡 시험

선택 채널은 알림톡이며 문자 대체 발송은 끈다. 필요한 항목은 `SOLAPI_API_KEY`, `SOLAPI_API_SECRET`, `SOLAPI_KAKAO_PFID`, `SHOP_ALIMTALK_TEMPLATE_ID`와 승인 템플릿이다. `SHOP_MESSAGE_CHANNEL=alimtalk` 선택과 실제 발송 활성화는 구분한다. 인증·승인 상태를 확인하기 전에는 실제 발송 플래그를 켜지 않는다.

변수는 `#{주문번호}`, `#{상태}`, `#{상품명}`, `#{샘플링크}`, `#{주문링크}`이다. 샘플 링크는 주문 확인 화면의 `#sample`로 연결한다. 직원 주문 링크와 고객 주문 링크의 권한을 구분한다.

운영자가 제공한 개인 번호는 비공개 시험 수신번호로만 사용한다. 같은 이벤트·같은 번호는 중복 제거되므로 직원·고객 역할을 나누어 시험한다. 과거 모의 발송 대기열을 실제 계정에 연결하지 않는다.

주문 확인 → 배송 중 → 배송 완료와 취소 알림을 확인한다. 발송사 접수번호·접수 결과와 실제 단말 수신·링크 열림을 따로 기록한다. 결과 불명 상태에서 문자로 대체하거나 같은 알림을 자동 재발송하지 않는다.

## 4. 현금영수증 발급 주체 확정

블로그페이에서 자동발급을 사용했다는 운영자 답변과, 새 독립 쇼핑몰에 동일 설정이 적용되는지는 별개다. 페이앱 판매자 설정과 기존 발급 내역을 대조해 결제사/쇼핑몰 중 발급 주체를 하나로 정한다. 상품의 과세·면세도 별도로 확정한다. 쌀 포함 상품이라는 이유로 합성 시험의 면세 설정을 복사하지 않는다.

현재 쇼핑몰 자동발급은 결제수단 6/7(계좌이체/가상계좌)을 대상으로 한다. 다른 수단은 자동발급 대상에 임의로 추가하지 않고 결제사 발급 여부를 확인한다. 카드 매출전표와 현금영수증을 구분한다.

실제 대상 거래의 발급번호·승인번호·금액을 대조하고, 부분취소 정정·전체취소도 확인한다. `20021`은 기발급 확인이 필요하다는 응답이다. 이때 재발급하지 않고 기존 영수증을 찾아 주문/결제번호·금액·발행번호·승인번호를 대조한다. 응답만으로 발급 완료 처리하지 않는다. 결과 불명은 관리자 대조 절차를 사용한다.

## 5. 결과 기록과 운영 전환

아래 양식을 각 시나리오에 복사한다. 실고객 개인정보·비밀키·서명된 관리자 링크·개인 수신번호를 공개 PR에 기록하지 않는다. 거래번호 원문과 승인 증빙은 접근이 제한된 운영 기록에 보관한다.

```text
환경 / 커밋:
실행 시각(한국 시간):
시나리오 / 모의 또는 실제:
주문번호 / 비공개 증빙 참조:
예상 금액 / 승인액 / 취소액 / 잔액:
실행 전 상태 → 실행 후 상태:
공급사 접수 결과 / 실제 단말 수신 결과:
영수증 발급·승인·취소 대조 결과:
예외 재현 조건 / 해결 / 동일 시나리오 재확인:
판정: 미실행 / 통과 / 실패 / 결과 대조 필요
```

운영자 리허설과 실제 공급사 결과를 모은 뒤 별도 운영 배포 요청에 따라 main 병합·배포를 진행한다. 현재 main은 커밋 자동 배포이므로 PR 승인과 운영 병합을 같은 것으로 취급하지 않는다. 미확인 항목을 완료로 가정하지 않는다.

공식 대조 근거: [페이앱 개발자 센터](https://www.payapp.kr/dev_center/dev_center01.html). 최신 모의 배포·회귀 결과와 접근 제한은 [출시 준비 현황](shop-first-release.md)을 기준으로 한다.
