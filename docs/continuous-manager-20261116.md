# 클라우드 개발 관리기와 연결 범위

형님의 지시를 프로젝트별 개발자에게 배정하고, 별도 검토자의 코드 판단과 격리된 검사를 대조한 뒤 태산이가 기술 인수합니다. 다음 업무는 이미 승인된 범위와 정확한 선행 후보에 묶인 경우에만 배정합니다. 기술 인수는 운영 배포 승인이 아닙니다.

등록된 클라우드 작업자의 두 연속 업무를 실제로 개발·검토·인수했습니다. 미래 작업자 예약, 새 CLI 세션 생성, 같은 세션 재개, 다음 업무의 태산이 배정 승인, 관리기 재시작 뒤 중복 실행 방지를 확인했습니다. 기존 UI 채팅 전체 연결과 24시간 운영 호스트 적용은 완료하지 않았습니다.

## 구현

| 구성 | 역할 |
| --- | --- |
| `fleet.py` | 서버에 등록한 호스트 검색, 세션 등록, 유효 기간과 생성 상한이 있는 미래 작업자 템플릿, 실제 전달 근거 검증 |
| `fleet_codex.py` | 공식 App Server의 로컬 세션 검색, 임대된 업무의 CLI 새 세션 실행·재개, 별도 코드 검토 |
| `continuous_manager.py` | SQLite에 실행 의도를 먼저 기록하는 감독 루프, 단일 리더와 세대별 임대, 재시작·중복 실행 방지 |
| `continuous_host.py` | 승인된 소스와 고정 검사 명령, 작업자·검토자 연결, 후보 동결, 기술 인수와 다음 업무 연결 |
| `scripts/run_continuous_manager.py` | 동일한 관리기를 한 번, 지정 횟수 또는 종료 신호까지 실행하는 클라우드 호스트 명령 |
| `/three-tier` | 페이지 단위 작업 현황, 전체와 표시 건수 구분, 명시적 버튼을 통한 연결·감독 상태 조회 |

신규 세션 생성은 실행 권한 부여와 다릅니다. 템플릿은 소유자가 등록한 호스트·프로젝트·유효 기간·생성 상한에 묶입니다. 작업의 정확한 버전, 승인 문서, 허용 경로, 기준 커밋과 현재 역할을 별도로 검사합니다. 세션을 발견하거나 모델이 답했다는 사실만으로 개발 완료나 테스트 통과를 표시하지 않습니다.

리더 임대가 만료돼도 이전 프로세스가 종료됐다고 추정하지 않습니다. 결과가 불확실한 실행은 자동 재전송하지 않으며 프로젝트 전체를 격리합니다. 명시적인 대조 요청도 실제 종료·실행 근거 없이 격리를 풀지 못합니다. 같은 소스를 공유하는 프로젝트는 독립 실행 대상으로 등록할 수 없습니다.

작업자 명령에는 실제 파일 접근 검사에 통과한 명명 권한 프로필을 사용합니다. 관리자 상태·역할 토큰·인증 홈·다른 디렉터리 접근과 명령 네트워크를 차단하고 검토 소스는 읽기 전용으로 둡니다. 기본 `workspace-write`나 프롬프트만을 인증 파일 보호 근거로 삼지 않습니다. 개발 쓰기 경계는 등록 저장소 단위이며 승인 경로는 후보 동결 전 별도 검사합니다. 허용된 소스 안에 운영 비밀을 넣어서는 안 됩니다. 연결된 검토 worktree 밖의 Git 공통 디렉터리는 명령에 열지 않으므로 일부 Git 명령은 차단될 수 있습니다.

현재 감독 루프에는 별도 신뢰 프로세스의 stop-only 종료 관측기가 연결돼 있지 않습니다. 프로젝트 비활성화·설정 변경 중 발생한 불확실한 실행을 자동 복구한다고 주장하지 않습니다. 해당 프로젝트는 격리를 유지하고 신뢰된 호스트의 정확한 종료 대조가 필요합니다.

## 확인한 연결과 남은 경계

소유 GitHub 저장소 5개와 Sites 24개의 메타데이터를 확인했습니다. Sites 24개는 서로 다른 Codex 대화 참조 11개를 공유합니다. 이 수는 작업자 수나 유지보수 승인 수가 아닙니다. 고객별 소스와 역할의 대응이 확인되기 전 자동 실행 대상으로 전환하지 않습니다.

전용 인증 프로필의 공식 App Server에서 등록된 CLI 세션 1개를 확인했습니다. Sites의 대화 참조 11개는 그 호스트에서 조회되지 않았습니다. 이는 현재 등록 호스트에서 미연결이라는 결과이며 계정 전체의 대화가 없거나 모든 UI 접근이 불가능하다는 뜻은 아닙니다. 기존 별도 Cloud UI 채팅 전체를 제어했다고 주장하지 않습니다.

향후 작업자는 생성 한도를 먼저 예약한 뒤 정확한 업무 임대가 생겼을 때 실제 CLI로 시작합니다. 반환된 세션 ID와 실제 실행 영수증을 대조한 뒤 연결합니다. 예약만으로 네이티브 세션이나 연결 성공을 표시하지 않습니다. 사용자가 UI에서 별도로 만드는 대화는 자동으로 관리 대상이 되지 않습니다. 공식 호스트에서 조회·재개 가능한 연결과 프로젝트 승인이 있어야 합니다.

호환성 실증에서 `thread/start`로 만든 첫 작업 전의 빈 세션은 서버를 정상 종료해도 저장되지 않았습니다. 세 차례의 한도 내 메타데이터 검사는 모델을 실행하지 않았고, `thread/resume`에서도 rollout이 없었습니다. 그 생성 기록과 불확실 상태를 보존합니다. 이 경로를 실제 연결 성공으로 계산하지 않으며 새 작업자는 위의 예약 후 실행 경로를 사용합니다.

예약 방식의 첫 네이티브 실증에서는 파일 변경과 실제 명령 3개의 종료 코드 0을 공식 저장 기록에서 확인했지만 원래 CLI 영수증을 보존하지 못했습니다. 이 작업은 인수하거나 재실행하지 않았습니다. 원래 프로세스 식별·종료 증거가 없으므로 기록만 보고 종료 코드나 종료 확인을 만들어 복구하지 않습니다. 이후 검증은 별도 작업 디렉터리·DB의 새 시나리오로 구분하고 기존 DB와 변경된 소스는 그대로 둡니다.

실행기는 이제 프롬프트를 전달하기 전에 비공개 DB에 프로세스 식별 기록을 남기고, 단계·고정 오류 분류·관측한 종료 상태와 이벤트 종류를 기록합니다. 원문 메시지·명령 출력·인증 값은 진단 기록에 넣지 않습니다. 프로세스 그룹이 사라졌다는 관측을 모든 후손의 종료 증거로 확대하지 않습니다.

별도 v2 진단에서는 실제 CLI 종료 코드 0과 명령 3개의 종료 코드 0을 기록했고, 공식 비실패 시작 경고가 `turn.started` 전에 도착해 파서가 거부한 것을 확인했습니다. 파서는 공식 형식의 경고만 최대 16개 허용하도록 수정했습니다. 경고는 명령·테스트 성공으로 계산하지 않으며 상위 오류·실패 턴·다른 종류의 작업 전 실행·ID 재사용은 계속 차단합니다. 이 수정으로 과거 결과 불명 기록을 소급 성공 처리하지 않습니다.

## 실행·상시 운영

관리기 코드와 역할 등록 DB, 고정 소스, 독립 검토 런타임, 개인 인증 경로가 있는 전용 클라우드 호스트에서 사용합니다. 비공개 구성 파일은 0600, 상태 디렉터리는 0700이어야 하며 API로 명령·경로·성공 플래그를 주입하지 않습니다. 키 원문은 Git·UI·로그에 저장하지 않습니다.

관리 DB·토큰을 담은 제어 디렉터리와 개발 소스·후보 디렉터리는 별도 트리여야 합니다. 제어 디렉터리 안에 소스나 후보를 넣으면 로더가 실행 전에 거부합니다. 실제 검사에서 디렉터리 접근까지 차단되는 배치만 허용합니다.

```sh
python scripts/run_continuous_manager.py --config /private/taesan/host.json --status
python scripts/run_continuous_manager.py --config /private/taesan/host.json --once
python scripts/run_continuous_manager.py --config /private/taesan/host.json
```

`host.json`은 실행할 코드의 깨끗한 커밋을 고정합니다. 기존 DB의 소유자 승인, 역할, 실행 상한과 템플릿을 사용하며 시작 명령이 이를 새로 만들지 않습니다. 종료 신호는 새 작업 선택을 중단하고 임대를 해제합니다. 재시작은 저장된 실행 의도를 대조합니다.

루프 구현과 24시간 호스팅 가용성은 별도입니다. 관리 VM의 수명, 프로세스 감독자, 인증 갱신, 영속 디스크 및 외부 상태 점검이 확인되기 전 `always_on_verified`는 항상 거짓입니다. 이번 변경은 운영 배포, 유료 호스트 생성, 운영 원장 쓰기, 결제·발송, 기존 예약 작업의 변경을 포함하지 않습니다.

`ops/taesan-continuous.service.example`은 전용 Linux 호스트용 감독자 초안입니다. 고정 경로와 서비스 계정을 실제 호스트에 맞추고, 격리 검사·재시작·종료·인증 갱신을 검증한 뒤 설치해야 합니다. 현재 관리 VM에서는 `/run/systemd`가 읽기 전용이어서 `systemd-analyze verify`를 수행하지 못했습니다. 설치·시작·자동 시작 등록은 하지 않았습니다. 서비스 파일만으로 상시 운영이 입증되지 않습니다.

## 검증 기록

고정 구현 커밋 `59c133458d82bd64aecf0ad96638b1ade76f9c04`에서 저장소 전체 테스트 **1,636개가 통과**했습니다. 실제 namespace 검사와 로컬 HTTP·JavaScript 검사를 포함합니다. 별도 v3 합성 실증에서는 모의 모델 제공자를 사용하지 않았습니다.

| 실제 v3 업무 | 개발 명령 | 별도 격리 검사 | 독립 코드 판단 | 태산이 결과 |
| --- | --- | --- | --- | --- |
| A · 실제 불리언 배송 분류 | 4개, 모두 종료 0 | 2개, 모두 종료 0 | pass | accepted |
| B · 실제 False의 인덱스 추출 | 2개, 모두 종료 0 | 3개, 모두 종료 0 | pass | accepted |

B는 A의 실제 인수 커밋에 묶어 사전 승인한 업무입니다. 감독기가 `approve_next`를 실행했고 같은 네이티브 개발 세션이 B를 수행했습니다. 생성 예약은 1건, 인수된 업무는 2건, 다음 배정 승인은 1건입니다. 개발자와 검토자는 다른 논리 역할·별도 인증 프로필·별도 모델 세션을 사용했습니다.

관리기를 다시 시작해 2회 조회한 뒤에도 작업 배정 수와 인수 상태가 같았습니다. 비공개 실행 진단에 남은 모델 프로세스 시작 기록은 전후 모두 4건(개발 2회·독립 검토 2회)이며 추가 모델 실행은 0건입니다. 이전 v1/v2 결과 불명 기록은 별도 DB와 소스에 보존했습니다.

공개 증거는 [continuous-manager-live-evidence.json](continuous-manager-live-evidence.json)에 있습니다. 네이티브 세션 ID는 해시로 기록하며 키·원문 로그·개인 대화 참조를 포함하지 않습니다. 모의 전송 테스트는 실제 모델 실행으로, 명령 종료는 독립 검사 통과로 바꿔 해석하지 않습니다. 업무 운영 성능을 새로 측정하지 않았으므로 기존 종합 기능 점수 66.7점을 올리지 않습니다.
