# 페이앱 연결 전 개선 · 1차 10개

2026-11-15 한국 시간. 사용자 요청에 따라 이후 플랫폼에 통합할 추가 개발 묶음이다. 기존 PR #20에서 작업하며, 이 묶음만으로 main 병합·운영 배포·실결제·실발송을 활성화하지 않는다. 검증 서버의 기존 배포와 이번 소스 변경을 구분한다.

## 구현한 10개

| 번호 | 기능 | 동작 |
|---|---|---|
| 1 | 실시간 주문 요약 | 상품·옵션·문구·보내는 분·주문자·설치 정보·합계를 한 화면에서 확인 |
| 2 | 요약 수정 바로가기 | 입력란으로 이동. 모바일 옵션은 접힌 선택 단계를 열고, 주문자 이름이 연동 중이면 해당 체크박스로 이동 |
| 3 | 글자 수 안내 | 문구 200자·보내는 분 140자의 현재 입력 길이 표시. 기존 입력 한도 유지 |
| 4 | 휴대폰 입력 검사 | 서버와 같은 형식을 검사하고 입력란을 떠나면 공백·하이픈 정리 |
| 5 | 영수증 번호 검사 | 사업자 10자리·개인 발급용 휴대폰 11자리 검사. 자진발급 시 불필요한 번호 입력 비활성화. 기존 초대장의 비활성 상태 유지 |
| 6 | 오류 항목 모음 | 누락·형식 오류를 모아 보여주고 해당 항목으로 이동. 수정된 오류 표시 해제 |
| 7 | 입력 진행 표시 | 현재 활성화된 필수 항목의 완료 수를 표시. 개인정보 동의를 자동 체크하지 않음 |
| 8 | 페이지 이탈 알림 | 입력 후 나가면 브라우저가 지원하는 범위에서 경고. 정상 제출에는 경고하지 않음 |
| 9 | 모바일 금액 바로가기 | 하단 합계와 주문 확인 버튼. 결제를 자동 실행하지 않으며 모달 열린 동안 가림 |
| 10 | 확인 후 초기화 | 취소하면 입력 유지, 지우면 옵션·문구·연락처·족자·중량·모바일 단계 초기화. 고유 시도 번호는 유지 |

개인정보를 localStorage/sessionStorage·쿠키에 저장하지 않는다. 위 UI만으로 결제·발송·영수증 발급이나 제작 접수를 실행하지 않는다. 현금영수증은 기존 기능의 번호 검사만 개선한 것이며 발급사 연결을 추가한 것이 아니다. 고객 안내는 카카오 알림톡과 샘플 링크 방식에 맞추고 문자 대체 발송은 활성화하지 않는다.

## 나중에 통합할 때

- `checkout_preflight.js`: 요청·저장 API 없이 DOM을 보조하는 모듈. 모바일 CSS도 이 모듈에서 삽입한다.
- `checkout.py`: 공용 HTML 렌더링 시 해당 파일을 읽어 `preflight_script`에 삽입한다. 배포 파일에 JS를 함께 포함한다. 현재 서버는 별도 번들러나 새 정적 경로가 필요 없다.
- `checkout.html`: 기존 HTML/JavaScript 뒤에 모듈을 실행한다. `data-can-submit`으로 기존 결제 가능 여부를 전달하고, `bellavita:checkout-reset` 이벤트로 기존 족자·중량·주문자 연동 상태를 동기화한다.
- 입력 기준: `#order`, `#amount`, `.product-options`, `choice*`, `sender`, `message`, `buyer`, `buyer_phone`, `same_buyer`, 영수증 필드와 기존 설치 정보 영역을 재사용한다. 다른 플랫폼에 옮기면 이 DOM 계약 또는 별도 어댑터를 제공한다.
- 적용 경로: `/i/{job}/{price}/order`, `/shop/order/{offer_id}`, `/shop/products/{product_id}`가 같은 공용 렌더러를 사용한다.
- 서버 검증·상품 스냅샷·고유 주문번호·결제 결과 불명 보호는 그대로 둔다. 클라이언트 검사를 서버 검증 대신 사용하지 않는다.
- DB 스키마나 데이터 이전, 새 외부 서비스·추가 계정은 필요하지 않다.
- 다른 플랫폼의 페이지 전환·라우터를 쓴다면 이탈 경고와 제출 상태 처리를 그 라우터에 맞게 별도 검증한다. 브라우저 이탈 경고를 임시 저장이나 복구 기능으로 취급하지 않는다.

## 재현과 검증

프로젝트 가상환경에서 실행한다. 아래 스크립트는 독립 임시 DB를 사용한다.

```sh
.venv/bin/python -m unittest discover -s tests
PYTHONPATH=tests .venv/bin/python tests/browser_checkout_preflight.py
PYTHONPATH=tests .venv/bin/python tests/browser_shop_catalog.py
```

새 브라우저 시나리오는 쇼핑몰과 초대장을 각각 모바일 390px·PC 1280px에서 검사한다. 직접 문구의 HTML 문자열이 실행되지 않는지, 오류 복구, 영수증 방식 전환, 수정 포커스, 초기화 취소/확정, 페이지 이탈, 메모리 이외 개인정보 저장 부재, 가로 넘침을 확인한다. 초대장 모바일 족자는 텍스트 캔버스의 접근성 문구와 그려진 픽셀을 확인한다.

정상 폼을 연속 제출하는 시험에서는 POST를 브라우저에서 가로채고 한 번만 전달되는지 확인한다. 서버에 주문을 생성하거나 실제 페이앱을 호출하지 않는다. 보내는 분 레이아웃 보조 응답도 모의로 제공한다. 이 검증을 실제 결제·카톡·영수증 성공으로 기록하지 않는다.

검증 중 발견한 오류: 입력란에서 버튼으로 이동할 때 발생하는 change 이벤트가 요약 버튼을 다시 생성해 첫 클릭을 잃을 수 있었다. 요약·오류 목록의 노드를 유지하고 값만 갱신하도록 수정했으며 입력 직후 수정 버튼을 누르는 동일 시나리오로 재확인한다.

검증 결과는 [1차 근거](validation/prepayment-batch-01.json)에 기록한다. 관리자 사용 안내는 [관리 매뉴얼](shop-admin-manual.md)을 사용한다.


## 이번 검증 결과

전체 단위·HTTP 회귀 180개가 83.956초에 통과했다. 새 브라우저 검사에서 쇼핑몰/초대장 각각 390·1280px, 기존 상품 브라우저 회귀에서 375·1280px를 확인했다. 새 시나리오의 주문 생성 0건, 예상 밖 주문 요청 0건, 가로 넘침·JavaScript 오류 0건이다. 정상 제출을 두 번 연속 시도해도 브라우저 가로채기에는 1건만 도착했고 결제 이동을 막는 이탈 경고가 없었다.

새 UI는 PR 소스에만 반영하며 현재 운영·독립 검증 서버에는 이번 묶음을 배포하지 않는다. 나중에 플랫폼 통합 시 위 파일과 이벤트 계약을 함께 적용하고 같은 브라우저 시나리오를 다시 실행한다.
