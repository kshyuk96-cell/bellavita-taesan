# Independent recovery receipts and owner grants

`RecoveryCatalog` preserves authenticated encrypted-backup receipts in a host-installed catalog backend separate from the original manager database. `publish(global_owner, encrypted_backup, backup_id)` requires a stored encrypted-object receipt and verifies the current original owner around transport callbacks. Catalog receipts bind scope, backup ID, encryption-key ID, ciphertext hash and byte count using HMAC-SHA256 with a separately supplied 256-bit trust key. Encryption and trust keys must differ. Neither key is persisted, returned or logged; raw/hex/base64/base64url secret labels are rejected before catalog publication.

`RecoveryTrust(scope, trust_key_provider, owner_authorizer, owner_validator)` is a dedicated independent trust configuration, not an unsigned HTTP input or fallback to a missing Store. The authorizer must validate an explicit owner recovery assertion and return its authenticated subject; the validator independently checks that subject's current recovery authority. Both are server-installed trusted Python callbacks. No default authorizer exists. The trust-key provider is also server installed, and should use a secret store distinct from ciphertext/catalog storage. Protecting this trust root and catalog access is necessary for disaster recovery.

`issue_grant(assertion, catalog_id, new_destination, ttl<=300)` signs the authenticated owner subject, recovery scope, issue/expiry times, exact new physical destination and random nonce. `restore(typed_grant)` verifies the current owner, grant signature/freshness, independent signed receipt, exact ciphertext hash/size, AES-GCM authentication and SQLite/schema/epoch integrity without opening or authenticating against the original manager database. Expired/future/forged grants, unsigned/changed receipts, wrong keys and existing destinations fail closed. Current owner authority is rechecked around secret/transport callbacks, after consuming the grant and after restore. The grant nonce is consumed with a create-only catalog write before destination writes. Partial/unknown outcomes require a fresh explicit owner grant; they never authorize automatic replay.

A new restored database receives the existing reconciliation-required quarantine marker. Running journal actions become uncertain, leader leases expire and their epoch advances; worker execution does not restart. Budget admission remains denied in a restored quarantined Store. This module duplicates the narrow existing SQLite quarantine procedure because the original GovernanceDurability owner-check Store may be gone; future changes to that procedure must update both implementations.

The catalog backend must provide durable, globally create-only writes, bounded authenticated transport and access control. Reusing nonces across independent writable catalog copies or rolling back the catalog can defeat replay protection: production configuration must use one authoritative anti-replay catalog. Local backend tests do not establish external availability, offsite durability, remote restore, key escrow or real customer recovery. Local crash cleanup of protected plaintext staging remains an operator responsibility. The backup snapshot retains existing manager credentials; quarantine must be explicitly reconciled before operational use.

The local proof removes the synthetic original manager database before recovery and verifies quarantine plus denied budget admission. It uses only local private fixtures and transient keys, and reports `offsite_verified: false`.
