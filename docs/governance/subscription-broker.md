# Managed Codex subscription refresh broker

`SubscriptionBroker(core, broker_ref, canonical_home, targets, refresh_callback=...)` is a trusted host registration. Each `SubscriptionTarget(project, member_id, role, home)` refers to an existing developer/reviewer membership and a distinct private profile. Paths, callbacks, auth values, and commands are never HTTP/model inputs. Profile directories must be owned and private; auth files are bounded, owned, private regular files without symlinks or hard links.

A newly registered generation is `unverified`; guarded CLI access is blocked until an owner-authorized refresh/distribution succeeds. `refresh_and_distribute(owner, expected_generation, request_key)` requires a currently authorized owner over every fixed target project, live role bindings, and idle registered jobs. An exclusive canonical-profile lock serializes refresh/distribution. Before the native operation, the broker journals `refreshing`; before copies it journals `distributing`. A generation compare-and-swap and exact canonical/target hashes prevent stale copies and changed requests. Before each individual copy, a new IMMEDIATE transaction rechecks owner, every target membership/configuration, idle state, and the canonical hash; the transaction remains held through the local file replacement. All files are replaced atomically with mode `0600`, including file and directory fsync. A completed identical request is idempotent only while its generation and files remain current.

`CodexSubscriptionRefresher(canonical_codex_host, project)` uses the installed app-server's `account/read` with `{refreshToken:true}`. The installed JSON schema explicitly states this proactively requests the normal managed refresh-token flow. External auth ignores that flag, so this implementation rejects external/API-key modes and never logs in, creates an account, provisions an API key, calls a model, or changes billing. It accepts only a managed ChatGPT account and verifies the private auth store's account identity remains unchanged. Native account details stay transient. The public receipt distinguishes a refresh request from an actual auth-file change; it does not invent an expiry time or claim every request rotates tokens.

Every target CLI metadata/model process must hold `profile_guard(token, project, member_id)` for its entire lifetime. The guard uses a shared lock, authorizes the assigned role, validates the current generation/file bindings, then rechecks caller/membership/configuration and credentials after the operation. The root host can register guard callbacks for both `_Rpc` and model process lifetimes; the canonical refresh host must be unguarded because it is already under the broker's exclusive lock.

Canonical and target homes have unified physical-directory (device/inode) unique ownership in the authoritative manager Store, claimed atomically before use. Another broker reference cannot reuse either kind of home. Equivalent Linux path spellings cannot claim another ownership slot; within-group physical aliases are refused. Exact same-reference reconstruction is idempotent. Legacy registrations whose complete ownership cannot be reconstructed fail closed for explicit migration rather than silently selecting a winner. Ownership is revalidated on every guard/refresh. This ownership and lock protocol coordinates one authoritative Store; profiles must never be shared across independent Stores or unguarded CLI consumers.

The lock coordinates participating transports. It does not prove that arbitrary unmanaged processes outside this registration are absent. Unregistered UI sessions are not controlled by this broker. Do not claim long-term safe distribution for a host until all target profile consumers use these guards and actual native refresh/metadata behavior has been verified.

A crash, partial distribution, caller revocation, unexpected account change, or profile mutation during use marks the generation `uncertain`. After restart, both guard entry and another refresh remain blocked. Restored/quarantined manager authority cannot refresh credentials or enter a profile guard. The module has no automatic replay, rollback to old refresh tokens, or release API. A managed CLI may independently refresh its target profile; this is detected, not silently harvested or overwritten from an older canonical snapshot. Owner reconciliation or a separately reviewed canonical-adoption protocol is required before continuing. This conservative boundary means fixture success alone does not establish an indefinitely self-healing authentication service.

`status(token)` is an owner/manager diagnostic over all fixed projects. It returns only broker reference, generation, state and counts; no tokens, auth JSON, profile paths, account identifiers, model text, or CLI arguments. Operational deployment and customer execution approvals remain separate.
