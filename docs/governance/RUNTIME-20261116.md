Node 실행은 고정 바이너리와 제한된 옵션을 사용한다. 원본 크기 한도는 64MiB를 유지하고, 런타임 해시는 별도 256MiB 한도로 계산한다. node_modules 경로를 소스에 섞어 읽기 전용 의존성을 가리는 방식은 거부한다. ERP 의존성은 고정 lockfile과 SRI를 검증한 뒤 lifecycle hook 없이 설치했다. npm 실행 전 원본 Git blob과 준비 파일이 동일한지도 검사한다.

협회용 Postgres 18 fixture는 공개 포트 없이 SELECT 1을 확인한 뒤 컨테이너를 제거했다. Chromium 설치 관측은 브라우저 사용자 시나리오 실행을 뜻하지 않는다. 협회의 미검증 시나리오는 중복 주문, 주문 상태, 비공개 메모, 서버 가격 스냅샷이다.

## 권한 및 복구 경계

구독 브로커는 같은 authoritative Store에 등록된 canonical·개발자·검토자 홈만 사용한다. 공유 잠금은 메타데이터 및 모델 프로세스 전체 생명주기 동안 유지한다. 갱신은 배타 잠금, 현재 소유자 권한, generation, 요청 멱등성을 검사한다. 초기 상태는 unverified이며, 결과가 불확실하면 자동 재실행하지 않는다. 프로필 홈을 다른 브로커에 중복 등록할 수 없다.

예약 갱신은 신뢰된 Python 조립 경로의 명시적 owner loader와 정확한 프로젝트 집합이 필요하다. JSON 설정만으로 소유자 권한을 만들 수 없다. 진행 중/불확실한 예약 작업은 재시작 후 자동 재생하지 않는다. 외부 갱신 전의 잠금 경합은 다음 주기에 다시 시도할 수 있다. 공유 작업 보고는 전체 관리 범위에 대한 조회 권한을 요구한다.

이번 실제 검증에서 모델 호출·유료 API 호출·고객 운영 쓰기는 0건이다. 키 원문은 증거 자료에 포함하지 않는다. 과거 실제 개발자→검토자→후속 개발 증거는 [PR 78](https://github.com/kshyuk96-cell/bellavita-taesan/pull/78)에 별도로 있다. 이번 구독/예약 검증을 새로운 모델 개발 실행으로 표현하지 않는다.

전체 루트 회귀 1,855개가 통과했다(구현 커밋 c0e1bfa). 관리기 단독 1,551개와 공통 코어 245개도 통과했다. 최초 GitHub CI는 보안 거부 테스트가 개발 환경의 Node 설치 경로에 의존하여 실패했다. 해당 3개 테스트의 설치기 경로를 실행 금지 sentinel로 명시해 환경 의존성을 제거했고, 관련 8개 테스트를 다시 통과시켰다. 실제 설치 검사는 신뢰된 Node/npm이 없는 CI에서 명시적으로 건너뛰며 보안 거부 검사는 그대로 실행한다. 최종 CI 상태는 PR의 checks가 기준이다.

## 배포 대상·비용·회복 결정안

확인한 Render 작업공간은 Simba’s workspace(`tea-dbqjaul6e07s73fcqmo0`)이다. [기존 자원 목록](runtime-render-inventory-20261116.json)의 서비스 6개는 변경하지 않았다. 기존 고객 서비스를 관리기로 전용하지 않는다. 특히 기존 main 자동 배포가 켜진 서비스가 있어 main 병합을 전환 수단으로 사용하지 않는다.

권장 전환은 별도 관리 프로세스와 격리 작업자 실행 위치를 구분하는 방식이다. 현재 Render MCP는 원격 명령 실행을 제공하지 않으므로 대상 호스트의 실제 격리 검증과 실행 접근 경로가 먼저 필요하다. 지금 클라우드에서 성공한 namespace 검사는 Render 호스트의 증거가 아니다.

조회한 기존 자원의 기본 계산은 compute 월 $28 + 디스크 13GB 월 $3.25 = $31.25이다. 세금·전송량·작업공간 요금 등을 포함한 전체 청구서는 아니다. 별도 최소 관리 서비스 예시 $7 + 1GB 디스크 $0.25 = 월 $7.25도 작업자·백업을 포함한 전체 시스템 견적이 아니다. 실제 실행 위치와 자원 요구를 검증하기 전 추가 비용을 확정하지 않는다.

전환 전 필수 조건은 대상 호스트의 실제 probe, 재시작 후 상태 복원, 호스트 밖 백업 및 복원 격리 검증, 네 고객별 연결 권한 확인이다. 실패 시 신규 작업 접수를 멈추고 불확실 작업을 격리한 상태로 유지한다. 복원한 Store는 기존 권한을 그대로 재활성화하지 않는다. 이번 변경에는 배포·신규 자원 생성·운영 쓰기·main 병합이 없다.
