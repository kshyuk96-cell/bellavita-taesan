# Encrypted recovery transport and rehearsal

`EncryptedBackup(GovernanceDurability(core), backend, secret_provider, staging_root)` wraps the existing SQLite backup/restore checks. `backend` must implement the host-installed `BackupBackend.put_if_absent(id, bytes)` and `get(id, max_bytes)` interface. No external provider is configured by default. `PrivateLocalBackupBackend` is a local proof adapter, not offsite storage.

`backup(global_owner, backup_id, key_id)` uses AES-256-GCM from cryptography with a fresh 96-bit random nonce. A canonical version/backup ID/key ID/nonce header is authenticated as additional data. The encrypted payload contains the exact SQLite recovery image and its integrity/schema/epoch metadata; no archive paths are extracted. The key provider receives a nonsecret key identifier and must return 32 secret bytes from a trusted local secret facility. Keys are never written to disk, returned, logged or requested in chat. Before creating a journal intent, cleartext backup/key labels are checked against raw, hexadecimal, base64 and base64url forms of the retrieved secret; matching labels are rejected with a generic error. The exact authenticated header is checked again before encryption, without scanning ciphertext. Python does not guarantee memory erasure; secret-provider process isolation remains an operator responsibility.

A durable local intent precedes storage. Transport and secret callbacks run outside database transactions, with owner authorization checked again before transport and after it returns. Once an ID has an intent it cannot be retried automatically; a timeout or interrupted/revoked operation remains uncertain even if the object was uploaded. Reconciliation/deletion/retention/key rotation are separate operator work, not automatically inferred. Backend implementations must provide create-only semantics, bounded reads, durable writes, transport encryption and their own access control. A boolean storage acknowledgement does not establish offsite availability or durability.

`restore_rehearsal(global_owner, backup_id, new_destination)` requires a stored local receipt and exact ciphertext size/hash, then verifies AEAD and the existing SQLite integrity/schema/epoch checks. The recovered database is new and marked reconciliation-required. Worker execution does not restart; uncertain actions are not replayed. Plaintext staging uses fresh private directories and is removed on success/failure. A host crash can leave private plaintext staging, so a dedicated protected temporary volume and operator cleanup are required. Backup objects contain encrypted database credentials; protect the key separately from the ciphertext.

The current implementation retains recovery receipts in the authoritative manager database. Complete disaster recovery without that database/receipt requires a separately secured authenticated receipt catalog, trusted key recovery and an explicit import procedure; those are not implemented. Real external upload/download, remote restore and offsite durability have not been demonstrated. Tests and the private roundtrip proof use only synthetic manager data and the local backend. No production, network or paid resource access occurs.
