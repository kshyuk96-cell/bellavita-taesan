# Quality consistency governance batch

The user's question was whether any worker with the same repository would produce the same quality. This batch addresses consistent requirements/approval/review inputs rather than claiming model equivalence. It does not touch customer order/invitation data, publish a site, deploy a service, start a model, merge main, create paid resources or develop the separate tester engine.

## Twenty concrete controls

| Item | Implemented behavior |
|---|---|
| 1 versioned baseline | Owner-approved immutable business contract versions. |
| 2 explicit draft | Manager creates exact scoped reviewable draft; no approval implied. |
| 3 owner CAS approval | Exact draft digest/prior revision/current config/current QA policy required. |
| 4 priorities | P0–P3 criteria retained for reviewer/manager. |
| 5 categories | Design, wording, pricing/behavior, completion, integration. |
| 6 QA mapping | Requirement IDs map to independently stored existing scenario IDs. |
| 7 reference identity | Same-project retained hash/config identity required; design cannot omit references. |
| 8 expiry handling | Expired/mismatched references stop baseline reuse, not silently disappear. |
| 9 source/config pin | Existing source task contract plus baseline current config/QA binding. |
| 10 owner lifetime | Revoked/expired original baseline owner invalidates reuse. |
| 11 proposal pin | Baseline snapshot captured before owner approval; old proposals cannot inherit a new baseline. |
| 12 task pin | Actual approved task carries exact baseline version/digest/revision/config/QA. |
| 13 developer packet | Same approved criteria, preserve rules and relevant QA context. |
| 14 reviewer packet | Same criteria digest, independent reviewer/current candidate binding. |
| 15 actual prompt wiring | Registered server getter fills both native prompt builders. |
| 16 late changes | Current packet binding is checked again at execution/review fences. |
| 17 legacy boundary | Missing baseline keeps legacy behavior; installed baseline cannot be omitted from task approval. |
| 18 critical evidence | Every mapped P0/P1 scenario needs executed/asserted/pass/evidence before acceptance. |
| 19 grouped reporting | Approved requirements, unfinished/unassigned work, review gaps, partial windows and current-vs-history acceptance. |
| 20 honest scope | No materialized reference bodies/image-viewing claim; no model quality/equivalence score or operational approval. |

Independent functional review reproduced an important delivery-size gap: a valid draft could create a 48,549-byte packet while native input is capped at 32 KiB. Fixed by 12,000 bytes requirement and 16,000 bytes mapped context bounds, exact relevant-QA projection without dropping any mapped case, and complete prompt preflight before the native execution checkpoint. The reviewer confirmed the fix; 114 related tests passed at that review point. Focused new tests: 39 passed, including actual loopback APIs and simulated native receipts. No native inference was performed.

A reference-only packet cannot prove that the developer or reviewer viewed an approved image. `materialized`, `body_transferred`, visual verification and business acceptance remain false/unmeasured. Actual material delivery is a remaining integration step.

The invitation-specific checklist is an unapproved proposal in `INVITATION-QUALITY-DRAFT.md`. It must obtain actual owner-approved reference identities and external tester mappings before becoming an active baseline.
