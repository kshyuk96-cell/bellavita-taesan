# Connect managed subscription supervision to the service loader

Native worker profile guards and periodic subscription refresh already existed, but `load_service` did not wire a registered broker into both. It now accepts an optional trusted local `ManagedSubscriptionRuntime` object. This object cannot be supplied through HTTP or JSON configuration.

A host bootstrap constructs the runtime with the canonical private profile, exact typed subscription targets, a private owner credential file and an installed native refresh callback. It calls `load_service(service_config_file, subscription_runtime=runtime)`. The service configuration must explicitly include supervision with a bounded `subscription_interval`. The owner must already have registered the project memberships and profiles. No enrollment, login, copying or refresh happens during binding.

During host loading, the runtime creates deferred profile guards for the exact developer and reviewer home/member/role pair. Each guard refuses use before binding. Binding requires exact correspondence between the host project set, every generated guard and broker targets, with one developer and one reviewer per project. It authenticates the worker credential files against those memberships and the owner against the broker. The runtime cannot be rebound or extended after binding. Profile use re-reads and authenticates the current exact worker credential, then holds the existing broker's shared profile guard.

The existing supervision loop receives that same broker and owner loader. Its durable due times suppress duplicate refreshes. Its broker refresh uses exclusive profile locking, preserves generation comparisons and quarantines uncertain updates. Existing admission, budget, source, review and host qualification fences continue to apply. A ready broker generation does not prove a subscription is unexpired; current native account/auth admission measurements are still required. There is no API-key fallback.

The ordinary CLI still loads services without this optional trusted object. A deployment must use an audited local bootstrap that constructs it; it is not activated by adding arbitrary providers or file paths to service JSON. The native refresher must be registered by that bootstrap, not selected from an HTTP callback, dynamic module name or prompt. An expired or failed login requires supported reauthentication; this feature does not automate an interactive login.

Validation uses synthetic private profiles and a fixture native refresh callback, not a real subscription refresh or model call. It covers unbound guards, missing schedule/scope, profile mismatch, duplicate guards, exact worker credentials, owner denial, single binding, file drift, and service-loop scheduled refresh. The existing real native worker pilot is separate evidence; this new loader wiring is not a production deployment or continuous-uptime claim.
