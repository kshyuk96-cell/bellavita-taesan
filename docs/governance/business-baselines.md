# Owner-approved business requirements and worker-independent handoff

`BusinessBaselines(core)` stores manager-created drafts and owner-approved immutable versions. A contract contains a version, 1–40 requirements (`id`, category, priority, criterion, mapped scenario IDs), up to ten retained reference identities (`reference`, SHA256, description), and bounded preserve constraints. Categories are design, copy, price behavior, completion and integration. Raw criteria are capped at 12,000 bytes; mapped QA context plus contract/coverage is capped at 16,000 bytes. Unknown scenario IDs and credential material are rejected. These are instructions/approval metadata, not an execution engine or a model quality score.

`draft(token, project, request_key, contract)` is scoped owner/manager and idempotent for the exact body. A draft is not approval. `approve(owner, draft_id, draft_digest, expected_revision=...)` checks owner, exact body/config/QA policy, version immutability, reference identity/hash/retention and prior revision. Active work prevents changing the baseline. A design baseline cannot be approved without retained reference identities. Retained metadata is not proof of current file materialization or human viewing.

Proposal creation snapshots the active baseline pin; owner batch approval binds the same version/digest/revision/config/QA policy to the task. A stale proposal needs a new snapshot. Store execution, claims, independent review and final acceptance recheck the task pin against the current approved baseline. A policy installed later does not silently upgrade old tasks. Prior baseline owner revocation/expiry, configuration/QA changes and reference expiry block reuse. No baseline preserves the existing legacy behavior.

The existing independent QA admission remains in place. For each P0/P1 business requirement, every mapped scenario must have an executed/asserted passing result with evidence. Missing or unmeasured mapped critical scenarios block technical acceptance even if unrelated tests pass. P2/P3 status remains visible rather than being promoted to verified business completion. This only consumes existing external report contracts; it does not create or run the separately developed tester engine. Current synthetic QA is still synthetic, with business/actual-project acceptance false.

`WorkerQualityHandoff` supplies the same criteria/preserve/reference identities and relevant expected QA rows to both developer and independent reviewer. The full external QA contract hash is preserved; a projection includes every mapped scenario and its adapter version, excluding only unrelated rows. Its binding digest is a data-integrity identifier, not a signature or authority grant. Reference bodies are not fetched/rendered, and image viewing is explicitly unmeasured.

The native driver receives packets from a registered server callback rather than caller-supplied task fields. It checks current task/pin/role and repeats the exact packet binding check at heartbeat fences. Both prompts include approved criteria as data, never execution permissions. The complete 32 KiB native prompt limit is checked before the native `before_run` checkpoint; oversize input is rejected, not truncated. Existing higher-level reservations/action journals still require their normal reconciliation if another layer has already recorded an attempt. Large manifests can still hit the complete limit even with a bounded baseline.

Strict authenticated operations routes add baseline draft/current/owner-approve, quality handoff and a grouped quality report. No reference path, body provider, callback, PASS flag, score, deployment authorization or credentials are accepted through these APIs. Same inputs and criteria reduce specification drift; equal output quality across different workers is not guaranteed.
