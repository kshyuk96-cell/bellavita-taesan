# 통합 대화의 읽기 계획 경계

`Planner(observe=None, clock=...)`는 현재 인증 프로젝트의 일상어를 **조회 제안**으로 바꾼다. 실제 조회, 권한, 데이터 근거, 처리 완료는 업무 어댑터와 서버가 결정한다. 인증·역할·확인 버튼·쓰기 권한은 모델 출력 필드가 아니다.

`propose(project, text, media=None, context=None)`는 `PlannerResult(state, plan, message, source)`를 반환한다. state는 planned/clarify/unsupported/unavailable/failed이고, source는 rules 또는 registered_model이다. 규칙 경로를 모델 이해력 측정으로 보고하지 않는다. 등록 모델 콜백이 실패해도 규칙 처리 성공으로 바꿔 보고하지 않는다.

호스트의 등록 콜백에는 project, 현재 text, 한국시간 today, 읽기 catalog, 현재 안전한 context, 분리된 media만 전달한다. 반환은 정확한 `{tool, arguments, follow_up?}` 또는 `{state: clarify|unsupported, message}`이다. 도구·필드·상태·날짜·개수를 서버에서 검증하며 모델의 자유 문장은 사용자에게 처리 완료 주장으로 전달하지 않는다.

현재 도구는 ERP 주문, 쇼핑몰 주문, 희망일출 상품/상담, 협회 권한/부고 조회뿐이다. 쇼핑몰·희망일출·협회 날짜 검색, 센터 필터, 집계, 엑셀은 연결되지 않았으므로 조건을 버리고 넓게 조회하지 않는다. ERP의 '완료'는 제작완료/배송완료 중 확인하고 '미완료'를 임의로 접수 상태에 대응하지 않는다.

context는 호스트가 새로 인증한 같은 직원·회사·프로젝트·대화에서 읽은 `{tool, arguments}`만 받는다. 짧고 명확한 조건 후속 요청만 같은 도구의 follow_up으로 제안한다. 모호한 'ㅇㅇ'는 조회 실행이나 변경 승인이 아니다. 대화 보관 기간과 프로젝트 격리는 상위 대화 게이트웨이의 책임이다.

기존 `MediaContext`를 재사용한다. 사진의 번호는 현재 사진 질문과 결합하지만 이미지의 지시·권한 문장은 업무 자료다. 사진만 오면 조회 의도를 묻는다. 음성만 오면 한 개의 해석된 음성에서 읽기 계획을 제안할 수 있으나 음성 'ㅇㅇ'나 변경 지시는 승인으로 간주하지 않는다. 모델·음성·이미지 API 연결 및 실기기 인식률은 이 모듈의 규칙 시험과 별개다.

현재 같은 도구의 조회 맥락에서만 “날짜만 오늘로 바꿔서 조회”, “주문번호만 13372로 바꿔”, “상태만 종결로 바꿔서 조회”처럼 조회 필드만 바꾸는 좁은 표현을 후속 조건으로 처리한다. 모델도 정확한 변경 필드와 follow_up=true를 반환해야 한다. 맥락 없음·주소/금액/수량 변경·특정 원본 주문 수정·추가 결제/발송 지시는 이 예외에 포함되지 않는다.

`PlannerResult.draft`는 부고 번호가 빠진 규칙 기반 clarify에서만 `Plan("association.obituary", {})`를 제공한다. 상위 게이트웨이는 이를 기존 Core의 누락 필드 초안으로 저장하며 조회를 실행하지 않는다. 같은 현재 초안에 대한 다음 단독 ID만 follow_up으로 보완한다. 동의·쓰기 지시·다른 대화·이미 완료된 조회의 단독 ID는 이를 채우지 않는다. 모델의 일반 clarify 결과에 도구 초안을 임의로 추가하지 않는다.
