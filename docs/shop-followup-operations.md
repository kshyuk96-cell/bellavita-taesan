# 알림톡·제작 파일·검수·현황판·자동 백업

PR #20에서 개발하며 운영 main 병합·실거래·실제 발송·프린터·운영 Sheets 쓰기는 이 범위에 포함하지 않는다.

## 관리자 진입과 사용 순서

대표 카톡 명령 `쇼핑몰 관리`가 반환하는 10분 유효 링크에서 운영 현황판을 볼 수 있다.
결제 확인 필요, 제작 보류·검수 대기, 배송 대기·진행, 알림 실패·결과 대조,
영수증 확인 필요를 최근 200건 기준으로 필터링하고 주문번호·문구·보내는 분으로 검색한다.
같은 주문이 여러 확인 항목에 포함될 수 있다. 기존 초대장 주문은 이 집계에서 제외한다.

신규 쇼핑몰 주문은 결제 확인 → 제작 파일 생성 → 사진 검토(해당 시) → 파일 검수 승인 →
공장 접수 → 배송 순서다. PNG와 PDF는 저장된 주문번호·문구·보내는 분·중량을 사용한다.
기본 300×900mm·150dpi는 검증 규격이다. 실제 출력 장비/족자에 맞는 규격을 입력하고 검수한다.
PDF는 래스터 이미지를 담은 단일 페이지이며, 이미지 해상도와 페이지 물리 규격을 일치시킨다.
신랑신부 사진은 별도 사진 검토를 유지한다. 새 텍스트 출력 레이아웃은 사진을 자동 합성하지 않는다.

`production_review_required`는 주문 당시 product_snapshot에 보관한다.
신규 주문에는 기본 적용하며, 기존 주문의 제작 접수 이력은 소급 변경하지 않는다.
기존 주문도 제작 파일을 생성하면 해당 주문은 최신 파일 검수 대상이 된다.
`SHOP_PRODUCTION_REVIEW_REQUIRED=0`은 구형 흐름을 명시적으로 유지하는 테스트/호환 설정이다.
완료된 물리 제작이 있다고 가정해 자동으로 재출력하지 않는다.

## 파일 버전과 제작 수신기

- 동일 주문·규격·렌더러·글꼴로 재요청하면 같은 파일 버전을 유지한다.
- 새 규격/렌더러/글꼴은 새 버전이며, 이전 승인으로 최신 버전을 접수할 수 없다.
- 승인/반려는 검수자(직접 입력), 접근 경로, 시각, 근거와 함께 저장한다.
- 파일의 SHA-256, 주문 내용 해시, 버전, 최신 검수 결정을 승인 시 대조한다.
- 관리자는 서명된 10분 링크로 검수 전 파일을 열 수 있다.
- 공장은 별도 Bearer 인증으로 현재 결제/부분취소 대조가 유효한 최신 승인 파일만 받는다.
- 수신기는 `production-artifact-v1` 기능을 선언해야 schema 3 이벤트를 받을 수 있다.
  PNG/PDF를 모두 내려받고 해시·포맷을 확인한 후 ACK한다. 실패 시 제작 대기열을 해제하지 않는다.
- 수신기 명령은 기존 `shop_receiver.py --server ... --data ...`를 유지한다.
  새 수신기는 `production-files/{주문번호}/{버전}.png/pdf`와 대기열의 artifact 메타데이터를 보관한다.
- 재검수 승인도 동일 주문의 원장·제작 행을 갱신한다. 실제 출력은 호출하지 않는다.

주요 저장: `shop_artifacts`, `shop_artifact_reviews`, `shop-production/`.
백업과 복구는 파일과 DB를 함께 보존해야 한다.

## 카카오 알림톡

[SOLAPI 알림톡 공식 문서](https://solapi.com/developers/api/messages-ata)와
[메시지 발송 공통 문서](https://solapi.com/developers/api/messages)의 ATA·pfId·templateId·variables 규격을 사용한다.
알림톡의 임의 고객 이미지를 템플릿 이미지인 것처럼 보내지 않는다. 주문별 문구 이미지가 표시되는
고객 상태 화면의 링크를 템플릿에 전달한다. MMS는 기존처럼 JPEG를 첨부한다.

아래는 설정 명세이며 이번 작업에서 실제 발송을 활성화하지 않았다.

```text
SHOP_MESSAGE_CHANNEL=alimtalk
SHOP_MESSAGES_ENABLED=1
SHOP_ALIMTALK_ENABLED=1
SOLAPI_API_KEY=<발송사 키>
SOLAPI_API_SECRET=<발송사 시크릿>
SOLAPI_KAKAO_PFID=<등록 채널 ID>
SHOP_ALIMTALK_TEMPLATE_ID=<승인된 기본 템플릿 ID>
```

템플릿 변수: `#{주문번호}`, `#{상태}`, `#{상품명}`, `#{샘플링크}`, `#{주문링크}`.
직원 주문링크는 24시간 서명 배송 링크, 고객 주문링크는 해당 주문 상태 화면이다.
선택적으로 `SHOP_ALIMTALK_TEMPLATE_CONFIRMED`, `_SHIPPING`, `_DELIVERED`, `_REFUND`, `_CANCEL`, `_RESUMED`로
이벤트별 승인 템플릿을 지정할 수 있다. 등록 템플릿과 변수 이름은 실제 승인본과 일치해야 한다.

채널은 알림 생성 때, 요청 본문은 발송 요청 직전에 고정한다. 채널 설정을 바꿔도 같은 알림을
다른 채널로 자동 중복 발송하지 않는다. `disableSms=true`로 발송사 SMS 대체발송을 끈다.
접수와 단말 수신은 구분하고, 결과 불명은 자동 재요청하지 않는다.
기존 발송사 대조·실패 확인 후 재요청 절차를 공통 사용한다.

## 자동 백업과 복구 시험

자동화는 기본 비활성이다. 독립 테스트 환경에서 실제 60초 간격으로 두 번 실행해 검증했다.
운영 Render 설정이나 운영 백업을 활성화한 것은 아니다.

```text
SHOP_BACKUP_ENABLED=1
SHOP_BACKUP_DIRECTORY=/var/data/shop-backups
SHOP_BACKUP_INTERVAL_SECONDS=86400
```

애플리케이션 유지 작업에서 실행하거나, 같은 단일 인스턴스에서 다음 전용 명령을 사용할 수 있다.
설정 경로는 TAESAN_DATA 바깥이어야 한다. 서로 다른 인스턴스/볼륨을 공유한다고 가정하지 않는다.

```bash
python scheduled_backups.py --data /var/data/taesan-data --watch
```

OS 파일 잠금과 SQLite BEGIN IMMEDIATE로 중복 실행·DB 쓰기를 제어하고,
데이터 파일의 전후 체크섬으로 복사 중 변경을 감지한다. 매번 별도 경로에 복구한 뒤
SQLite 무결성, 파일 목록/체크섬, 전체 SQL, 제작 PNG/PDF의 DB 해시까지 대조한다.
통과한 `.pending-...` 보관본만 `shop-...` 정상 보관본으로 바꾸며, 실패는 `.failed-...`로 보존한다.
실패해도 이전 정상 보관본을 덮어쓰거나 삭제하지 않는다. 실행 이력은 `shop_backup_runs`와 관리자 화면에 남는다.
자동 삭제·외부 저장소 전송은 구현하지 않았다. 운영 디스크의 실제 경로/용량과 별도 보관소는 운영 검증 범위다.

기존 초대장/외부 파일 작성자가 멈추지 않은 상태의 전체 애플리케이션 이전에는
기존 `manage_data.py --service-stopped` 절차를 유지한다. 이번 온라인 백업은 협력하는 쇼핑몰 DB/제작 파일 경로를
검증하며, 독립 파일 작성자가 복사 중 변경하면 실패로 기록한다.
복구 시에는 별도 새 디렉터리에서 실발송·실결제·실원장 쓰기를 끈 채 먼저 확인한다.
