# 결제 주문 → 제작 접수·원장 사본

사용자 계정·가맹점 설정과 별개로 진행할 수 있는 후속 연결부다. 기존 PR #20에서 이어서
구현하며, 같은 고유 주문번호를 알림·결제·배송·원장·제작 대기열에 사용한다.

## 처리 흐름

1. 쇼핑몰 결제 확인 트랜잭션에서 주문별 `ready` 접수를 한 번 생성한다.
2. 주문에 신랑신부 사진이 있으면 사진 검토 상태에서 기다린다. 관리 화면에서
   사진이 실제로 로드되고 대표가 두 얼굴을 확인한 뒤 `사진 검토 완료·제작 접수`를 누른다.
   기존 초대장의 사진 검토 기록과 같은 테이블을 사용하되 쇼핑몰 주문만 처리한다.
3. 공장 수신기는 별도 인증 키로 접수 한 건을 120초 동안 선점한다. 다른 수신기가
   동시에 같은 건을 선점하지 못한다. 선점 기간이 끝난 건은 다시 받을 수 있다.
4. 수신기는 로컬 원장 사본과 제작 대기열을 같은 SQLite 트랜잭션에서 저장한다.
   각각 주문번호에 UNIQUE 제약을 두어 재전달돼도 새 제작 건을 만들지 않는다.
5. 서버에 원장·제작 대기열 참조번호를 전달해 수신을 확인한다. 확인 전에는
   `awaiting_ack`, 확인 후에는 `pending` 제작 대기 상태다. 접수 확인은 출력 완료가 아니다.
6. 취소·부분취소가 확인되면 아직 전달하지 않은 제작 접수를 보류하고, 이미 전달한 건에는
   `hold` 접수를 추가한다. 수신기는 원장과 제작 대기열을 보류로 바꾸며, 오래된 `ready`가
   나중에 도착해도 이 상태와 더 큰 취소금액을 되돌리지 않는다.

물리 출력기나 실제 족자 제작 프로그램은 이 수신기에서 호출하지 않는다. 이후 제작 실행기는
`pending` 대기열을 이어받아야 하며, 실제 출력 직전의 주문 상태 확인과 이미 시작된 제작의
취소 대응은 해당 시스템의 업무 정책에 따라 연결한다.

## 전달 데이터

주문번호, 행사·상품, 실제 옵션·문구·보내는 분, 주문자 연락처, 설치 장소·주소·시각,
제작 수량 1개와 쌀 중량, 검토된 사진 참조, 결제번호·원금·취소 누계·잔액을 전달한다.
문구를 상품의 최신 값으로 다시 만들지 않고 주문 당시 저장된 값을 사용한다.
현금영수증 식별번호·서버 자격증명은 이 전달 데이터에 포함하지 않는다.

원장 사본은 `receiver.sqlite3`의 `order_ledger`, 제작 대기열은 `production_queue`,
재전달·수신 확인 이력은 `received_events`에 보관한다. 원장의 금액은 원금과 취소 누계·잔액을
구분한다. CSV는 수동 검토·시트 사본 가져오기용이며 운영 Google Sheets에 자동으로 쓰지 않는다.
수식으로 해석될 수 있는 입력은 CSV에서 문자로 이스케이프한다.

## 연결 계약

서버 설정: `SHOP_HANDOFF_ENABLED=1`, 별도의 32자 이상 `SHOP_HANDOFF_SECRET`.
키는 환경 설정에만 보관한다. 기존 카카오 스킬 키·관리 화면 서명 키를 재사용하지 않는다.
수신기도 같은 연결 키를 환경 변수로 사용한다. 기능 설정을 마치지 않아도 서버의 접수
기록은 보존되며 다른 개발·검증 흐름을 막지 않는다.

```sh
python shop_receiver.py --server https://검증서버 --data /수신기/전용데이터 --consumer factory
# 지속 수신:
python shop_receiver.py --server https://검증서버 --data /수신기/전용데이터 --consumer factory --watch
# 원장 사본을 새 CSV로 내보내는 단일 실행:
python shop_receiver.py --server https://검증서버 --data /수신기/전용데이터 \
  --export-csv /검토사본/orders-새파일.csv
# 수신 확인이 끝나지 않은 상태도 포함하여 별도 DB 백업:
python shop_receiver.py --data /수신기/전용데이터 --backup /보관소/receiver-새파일.sqlite3
```

로컬 검증용 CA가 필요한 경우 `--ca-file`로 지정한다. TLS 검증을 끄거나 리디렉션된
주소로 인증 키를 보내지 않는다. 서버의 태산이 데이터 폴더를 수신기 폴더로 지정하지 않는다.

| API | 요청 및 응답 |
| --- | --- |
| `POST /shop/handoff/claim` | Bearer 인증 + JSON `consumer`. `job:null` 또는 선점한 접수·스냅샷·SHA-256·수신 확인 토큰 반환 |
| `POST /shop/handoff/ack` | 같은 인증 + `consumer`, `event_id`, `lease_token`, `references`의 `ledger`·`production` 참조번호 |

토큰·수신자·참조가 맞는 완료 확인은 재전송해도 성공한다. 확인 응답만 유실된 경우 수신기는
저장한 확인 요청을 먼저 재전송한다. 선점이 만료·교체됐으면 새 전달을 받아 같은 원장·제작
행을 재사용한다. 수신 중 결제가 취소되면 `payment_changed`로 거절하고 로컬 제작도 보류한다.

접수 본문은 한 번 생성된 후 바꾸지 않으며, 소비자는 본문 SHA-256과 주문번호·스키마·금액을
검사한다. 금액·문구가 다른 접수를 같은 식별자로 덮어쓰지 않는다. `hold`는 `ready`보다 우선
전달한다. 수신기의 업무 데이터와 확인 토큰은 접근 제한된 전용 폴더에 보관한다.

## 기존 주문과 백업

이미 결제된 과거 주문에는 관리자 화면의 `후속 접수 준비`로 개별 접수를 만들 수 있다.
과거 주문을 한꺼번에 자동 제작 접수하지 않는다. 이미 접수한 주문을 다시 준비해도 한 건이다.
취소 주문을 이 버튼으로 제작에 복원하지 않는다.

서버의 `shop_handoff` 테이블은 기존 데이터 백업·복구에 함께 포함한다. 수신기 백업에는
확인 응답 유실 시 재시도할 상태까지 포함한다. 수신기를 중지한 상태에서 백업 DB를
전용 폴더의 `receiver.sqlite3`로 복구한 뒤 재시작하면 저장된 확인 요청부터 처리한다.
원장과 제작의 유일 주문번호를 유지해 복구 후에도 중복 접수하지 않는다.

## 검증 범위

테스트는 독립 HTTP/HTTPS 서버·사본 SQLite·모의 결제로 진행한다. 대표 사진 검토,
공장 수신, 취소 보류를 브라우저에서도 확인한다. 운영 원장 쓰기·실제 인쇄·실제 가맹점 거래는
이 결과에 포함하지 않는다. 설정 작업이 남더라도 코드·사본·장애 복구 검증은 독립적으로 진행한다.
