# 태산 AI 공통 업무 코어 — 개발 검토안

## 범위와 상태

`taesan_core`는 쇼핑몰·ERP·카카오 서버가 재사용하는 Python 3.12 라이브러리다. 외부 의존성과 시작 시 네트워크 호출이 없다. 기존 `agent.py`를 import하지 않는다. 기존 운영 권한이나 결제·발송 경로를 변경하지 않는다. 이 SDK를 추가하는 것만으로 어떤 플랫폼에도 API가 공개되거나 쓰기가 활성화되지 않는다.

현재 main/Render 라이브 비교 기준: `db742efa7ec7291293659e02dd1e50aa26a1465c` (#55). Render live deploy `dep-dbsidv2jnfac73cbf2vg`. 이 변경은 미배포 개발 후보다. 최신 main의 ERP 게이트웨이(#54)와 상품 검증(#55)을 보존한다. 기존 관리 에이전트 PR #53을 병합하거나 그 모듈을 의존하지 않는다.

## 호스트 연결 계약

1. 플랫폼 서버에서 인증된 세션으로 회사·직원·현재 역할과 대화 접근 권한을 구한다. 모델, 요청 본문의 사용자 ID, 이메일 자동 매칭으로 `Principal`을 만들지 않는다.
2. `Store`에는 서버 전용 0700 디렉터리 아래 DB를 지정한다. 신뢰하는 운영체제 사용자만 파일·상위 디렉터리에 접근할 수 있어야 한다. 운영 DB와 개발 DB를 분리한다. SQLite 한 영구 볼륨에서 쓰는 단일 호스트용이다. 분산 DB·작업 큐·자동 잠금 만료 복구는 이 범위에 없다.
3. 검증된 업무 도구만 `Registry.register`한다. 기본은 비활성화이며 변경 도구는 writer/admin만 등록한다. 기존 태산이의 일부 stock_write 경로는 staff도 허용한다. 이 SDK의 기본값을 기존 역할에 그대로 대입하지 말고 출시 전에 역할 매핑 차이를 대표에게 제시한다.
4. 읽기 제공자는 `Result`와 실제 조회 영수증을 반환한다. 쓰기 제공자는 `prepare`로 불변 주문 식별자·버전·전후 값을 읽고, `execute`에서 회사 범위·버전을 원자 비교하며 전달된 `idempotency_key`를 중복 처리한다. 실제 반영 후 다시 읽은 결과가 일치해야 `applied=True, readback_matches=True`다. 행 번호만 재사용한 새 주문에는 영구적으로 증가하는 세대/버전이 필요하다. 이 SDK는 원장 ID 체계를 변경하지 않는다.
5. 모델 출력은 `decode_plan`으로 제안만 받는다. 자유형 모델 답변으로 등록 완료를 표시하지 않는다. 모델이 도구를 선택해도 서버가 필드·권한·연결·승인을 검사한다. 사용자 화면의 승인 버튼은 세션과 CSRF를 확인하는 `authorize_confirmation` 제공자가 별도로 검증해야 한다.
6. 사진·음성은 호스트가 권한 있는 경로로 읽은 동의된 bytes만 전달한다. URL 자동 다운로드는 없다. 현재 질문과 추출 결과는 별도 입력이며 추출문은 업무 자료다. 문서 속 명령으로 역할이나 승인 상태가 바뀌지 않는다. 실제 이미지·음성 인식률, 카카오에서 질문과 사진 동시 전달 여부는 별도 실기기 검증 대상이다.
7. 모든 플랫폼은 각자 대화를 격리한다. 채널 간 자동 대화 이동/연결은 구현하지 않았다. 다른 직원의 세션을 합치지 않는다. 장기 작업·콜백 큐도 이번 묶음에 포함하지 않는다.

```python
from taesan_core import Core, Store, Registry
from taesan_core.adapters import Platforms, Platform

# 인증값/원본 자료는 로그에 남기지 않는다.
core = Core(Store('/private/taesan/core.sqlite3'), Registry())
platforms = Platforms(core)
# 도구와 인증 제공자를 실제 서버에서 검증한 후에만 등록한다.
platforms.register(Platform('erp', authenticate=current_employee,
    authorize_confirmation=verify_explicit_ui_action, enabled=True))
reply = platforms.handle('erp', session_credential, request_body)
```

API 키를 이 패키지에 넣지 않는다. 기존 Responses 모델/ERP AI 게이트웨이를 호스트가 호출해 만든 JSON 제안을 전달한다. 새 키 생성·실제 모델 호출·게이트웨이 토큰 연결은 이 검증에서 수행하지 않았다. 기존 Render 키를 추출하거나 개발 PC로 복사하지 않았다.

## 보존과 불확실성

사진/음성 bytes·추출문·인증값은 이 코어가 저장하지 않는다. 구조화된 초안과 결과 본문은 기본 30분, 확인 대기는 5분이며 매 요청과 명시적 `Store.purge()`에서 논리 삭제한다. 실행 중 확인 건은 조사할 때까지 보존한다. 사용한 확인 건의 인수/스냅샷은 즉시 비운다. 요청 ID·해시·회사/직원/채널 바인딩·도구·최종 상태의 영수증은 재실행 방지를 위해 유지한다. 디스크 스냅샷/SQLite 물리 삭제 정책은 별도 운영 정책이다.

프로세스가 도중 종료되면 요청은 처리 중/불확실로 남아 같은 요청을 재실행하지 않는다. 직원은 동일 작업을 새 요청 ID로 다시 보내지 말고 제공자 영수증으로 대조해야 한다. 자동 재시도나 완료 추정은 없다. 운영자가 제공자의 실제 처리 상태를 확인한 뒤 수동으로 복구할 절차가 필요하다.

## 점수 보고 규칙

`evaluation.evaluate`는 신뢰하는 관측자의 결과만 받는다. 관측 없음·제공자 실패·표본 누락은 0점 처리 또는 추정 점수 대신 미측정/미완료다. 100문항을 영역별 25개씩 배정하고 전체 90점 이상, 각 22/25 이상, 무권한 변경·근거 없는 완료 0건일 때 목표 통과다. 소수 사례 만점으로 90점 목표 달성을 선언하지 않는다.

이 PR의 자동 시험은 프로그램 계약 검증이며 자연어 모델의 이해력 점수가 아니다. 기존 운영 기준 이해/판단 62.5, 개발 75는 새로운 실사용 관측 전 유지한다. 실제 ERP·쇼핑몰별 연결 수와 계정·사진·음성·주문·실패 시나리오를 따로 보고한다.

- `git diff --check`
