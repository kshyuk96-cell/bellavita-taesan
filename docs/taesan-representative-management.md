# 태산이 대리 관리 10개 — 개발 검토안

## 목표와 현재 상태

대표는 태산이 한 창에서 지시·미팅하고, 태산이는 등록된 개발 에이전트의 배정·진행 조정·독립 검증을 맡는다. 승인된 위임 범위 안의 개발/시험은 작업마다 대표에게 재승인을 요구하지 않는다. 범위 밖 작업은 정확한 결정 묶음으로 올린다.

기존 유지보수 PR #59 `adb3ec4`를 재사용하는 후속 개발 후보다. 네 고객 소스/서비스 등록부, Store 권한·lease·저장소 예약, Coordination 라우팅/정책, supervisor 독립 검증, Workflow 지시 변경을 확장한다. PR #53/#59의 통합·운영 반영을 자동 승인하지 않는다.

현재 기능은 라이브러리 및 기존 관리 서버의 인증된 `/v1/representative/` API다. 실제 고객 네 곳의 실행 플래그는 켜지 않았고, 기존 다른 Codex 채팅창을 자동으로 읽거나 통제하지 않는다. 실제 배정은 연결이 검증된 수신기/워커 또는 부모 런타임의 네이티브 에이전트에 한정된다. 상주 호스트·타이머·실제 서비스 연결은 별도 단계다.

## 위임 권한과 변경 차단

새 위임 정책은 `pending_approval`에서 시작한다. 대표의 `activate(id,fingerprint)` 후에만 지정 관리자가 사용할 수 있다. 개발/시험 외 동작을 담지 않는다. 소유자 인증값을 관리자나 워커에게 전달하지 않으며, 관리자 역할을 소유자로 위장하지 않는다.

현재 구현은 최대 100개 작업, 최대 7일의 유한한 위임을 지원한다. 실제 적용 시 대표에게 기간·개수·경로·검증 항목을 한 묶음으로 제시한다. 정책은 제자리에서 넓히지 않고 새 버전/승인으로 등록한다. 임계치를 임의로 늘리지 않는다. 관리자가 출처 관측을 재조회해 같은 승인 작업의 오래된 근거를 갱신하는 것은 작업 수를 중복 차감하지 않는다.

`SourceProof`는 호스트에 등록된 관측기가 실제 프로젝트/출처/브랜치/커밋/근거/시각을 반환해야 한다. 요청이나 모델이 관측기를 선택할 수 없다. 실행 전 큐의 근거는 300초 이내여야 하며 오래되면 관리자가 재조회한다. 이미 실행 중인 작업은 최초 근거 나이만으로 끊지 않지만, 위임 만료·철회·설정 변경·인증 철회는 계속 검사한다.

승인·claim·heartbeat·report·부모 작업 안의 유지보수 시험·에이전트 수신 확인에 위임 검사를 연결했다. 실제 파일 변경 범위와 모든 등록 검증은 독립 supervisor가 다시 확인한다. 범위 밖 파일이나 보고 후 바뀐 artifact는 검토 완료로 처리하지 않는다. 위임 철회 시 미시작 작업은 취소하고 시작/보고된 작업은 확인 필요로 남겨 저장소 예약을 보존한다. 이미 독립 검토된 후보를 소급 수정하지 않는다.

## 에이전트 연결의 의미

- 등록에는 실제 발급된 프로젝트 범위의 worker 계정이 필요하다. 세션 ID는 연결 참조이며 자유로운 URL·프로그램·환경변수 입력으로 실행기를 만들지 않는다.
- `Coordination.route(...,worker_hash=...)`로 선택한 에이전트의 정확한 계정에만 배정한다. 기본 라우팅 동작은 유지한다.
- 전송 성공은 실행 성공이 아니다. 실제 worker가 정확한 Store 작업을 claim하고 lease로 확인해야 한다. 전송 응답이 불확실하면 자동 재전송하지 않는다.
- `RepresentativeWorker`의 기본 실행기는 미연결이다. 실행 콜백에는 원문 인증값·lease를 전달하지 않으며 비공개 heartbeat를 통한 서버 검사를 제공한다. 실행 도중 중단되면 재시작 시 같은 코드를 다시 돌리지 않는다.
- 실행 콜백은 실제 프로젝트 코드에 맞는 격리 환경을 호스트가 제공해야 한다. 라이브러리·등록 사실·HTTP 응답만으로 OS 격리나 기존 Codex 창 접근이 성립하지 않는다.

## 관리 API

기존 `manager_bridge.server`에서 인증·같은 출처/CSRF·엄격한 JSON 검사 뒤 새 라우터를 호출한다. 모든 요청은 정확한 필드만 허용한다. source 관측기·별칭·전송기·실행기·독립 검증 명령은 서버 설정에서만 공급한다.

- `POST /v1/representative/intake`, `/intake/task`
- `/delegation/propose`, `/delegation/activate`, `/delegation/authorize`, `/delegation/revoke`
- `/agents/register`, `/agents/probe`, `/agents/enqueue`, `/agents/send`, `/agents/ack`, `/agents/report`, `/agents/control`
- `/meetings/prepare`, `/meetings/confirm`
- `/packets/prepare`, `/packets/decide`
- `/review/verify`, `/review/changes`, `/review/blocker`
- GET은 등록 에이전트/수신함/접수/위임/미팅 후속/승인 묶음의 프로젝트 권한을 다시 확인한다.

이 경로들은 개발용 관리 서버의 인터페이스이며 실제 고객 서버에 게시하지 않았다. 키·콜백·외부 실행 명령을 요청 본문으로 등록할 수 없다. 화면이나 본문에 '승인'이 있다고 activate/decide를 실행하는 텍스트 승인 경로는 없다. 주 관리자가 대표와 대화하는 호스트에서 실제 사용자 승인과 정확한 검토안을 연결해야 한다.

## 검증 결과

Python 3.12, 임시 TAESAN_DATA·가상 계정/스킬 비밀값·등록된 모의 제공자로 전체 654개 회귀 시험 통과(기존 463 + 신규 191). 신규 시험에는 실제 로컬 HTTP 인증/역할/입력 검증과 정확한 작업 ID claim 검증을 포함한다. `git diff --check` 통과.

기존 회귀와 새 위임/수신/미팅/HTTP 시험을 함께 실행한다. 실제 모델/결제/문자/고객 시트/운영 서버는 시험에 사용하지 않는다. 가상 계정과 임시 TAESAN_DATA를 사용한다.

추가로 현재 부모 런타임의 실제 하위 에이전트 `/root/management_fixture_worker`에 합성 프로젝트 시험을 배정했다. 대표 정책 1회로 관리자가 2개 작업을 승인했고, 그중 1개를 실제 네이티브 에이전트가 수행했다. 고유 fixture 시험 4개가 통과했으며 부모가 등록된 두 검증 명령으로 독립 재시험하고 HEAD·artifact·깨끗한 작업폴더를 대조했다. 미팅 후속도 독립 검증 기록을 조회했다. 개별 작업 대표 승인은 0회다.

근거 요약은 `docs/taesan-representative-proof.json`, 전체 로컬 기록은 비공개 검증 디렉터리에 있다. 미사용 두 번째 가상 작업은 취소하고 가상 위임도 철회했으며, 검증된 후보는 보존했다. 이 사례는 실제 고객 Codex 세션 연결이나 운영 90점 달성의 증거가 아니다.

```sh
python -m unittest discover -s tests -q
git diff --check
```

실제 연결 전에는 네 프로젝트의 수신기/격리 실행기와 대표용 인증을 한 번에 준비하고, 위임 범위를 대표에게 묶어 제시한다. 현재 시간별 자동 개발·운영 예약·상시 실행·실제 배포 설정은 그대로다. 운영 AI 점수는 이해/판단 62.5·개발 75를 유지하며 새 실사용 평가와 프로그램 회귀 시험을 구분한다.
