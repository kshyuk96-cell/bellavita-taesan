# 자동 초대장 연동 상품·족자 미리보기 개발 지시서

2026-11-15 한국 시간 기준. 기존 벨라비타 구현을 재현하거나 이어서 개발하는 에이전트에 전달하는 문서다. 신규 쇼핑몰 전면 개발이 아닌 기존 초대장 주문서의 상품 연결과 실시간 족자 표시가 대상이다.

## 1. 개발 목표와 작업 위치

초대장에 행사별 상품과 가격을 연결한다. 고객이 초대장의 주문 버튼으로 들어와 쌀 중량·축하 문구·보내는 분을 입력하면, 신랑신부 사진이 포함된 족자 미리보기에 즉시 반영되게 한다. 같은 화면에서 주문자와 설치 정보를 확인하고 페이앱 결제로 이어진다.

- 저장소: `kshyuk96-cell/bellavita-taesan`
- 이어서 작업할 위치: 기존 PR #20, `codex/shop-backend` → `main`. 착수 시 최신 PR HEAD와 main을 다시 대조한다.
- 기존 고객 경로: `/i/{job_id}/{price}/order`
- 초대장 가격 경로: 현재 `93500`, `99000` 두 값이다. 임의 가격을 URL에 넣어 주문할 수 있게 만들지 않는다.
- PR #20의 공개 상품 4개와 `/shop/products/{product_id}`, `/shop/order/{offer_id}`는 별도 경로다. 공개 상품을 기존 초대장별 주문 상품과 같은 것으로 취급하지 않는다.
- main 병합은 기존 Render 서비스 자동 배포를 일으킬 수 있다. 이번 지시서만으로 운영 병합·실결제·실발송을 활성화하지 않는다.

## 2. 현재 만드는 방식

현재 미리보기는 고객의 입력마다 새 사진을 생성하는 방식이 아니다. 기존 상품 이미지 위에 족자 배경, 신랑신부 사진, 중량 이미지, 문구, 보내는 분을 HTML/CSS 레이어로 합성하고 JavaScript로 갱신한다.

초대장 생성 시 행사별 상품 정보를 스냅샷 파일로 저장한다. 고객 주문 시에는 해당 스냅샷을 읽고 주문 입력과 상품 조건을 SQLite에 다시 보관한다. 브라우저의 실시간 그림, 저장된 주문 정보, 제작용 고해상도 파일을 각각 구분한다.

| 파일 | 역할 |
|---|---|
| `invitation.py` | 행사 정보 추출, 가격별 상품 연결, 초대장 HTML과 주문 스냅샷 생성 |
| `blogpay.py` | 기존 블로그페이 상품 조회·연결·복사 관련 처리 |
| `checkout.py` | 상품 정보 파싱, 주문 화면 구성, 서버 검증·금액 계산·결제 처리 |
| `checkout.html` | 주문서 공용 HTML/CSS/JavaScript와 족자 실시간 배치 |
| `scroll_sender.py` | 보내는 분 텍스트의 표시 구조 분리 |
| `agent.py` | 주문·미리보기 보조·결제 통보·고객 확인 화면 HTTP 경로 |
| `production_files.py` | 별도 제작 파일 생성·검수 흐름. 화면 미리보기와 구분 |

## 3. 개발 작업 다섯 묶음

### A. 행사별 상품을 연결하고 조건을 보존한다

1. 기존 초대장 생성 흐름을 재사용해 행사명, 행사일시, 장소, 설치 주소, 원본 초대장 주소, 신랑신부 사진과 크롭 정보를 확보한다.
2. 현재 자체 주문서 경로는 `invitation.find_order_products()`로 행사에 대응하는 두 가격의 블로그페이 상품을 찾고 `checkout.product_snapshot()`으로 상품 사진·선택지·가격을 읽는다. 필요한 두 상품이 없으면 운영자에게 등록 상태를 알린다. 모든 모드에서 새 상품이 자동 생성된다고 가정하지 않는다.
3. 별도 블로그페이 직접 연결 흐름의 `find_links()`와 `BLOGPAY_INVITATION_AUTO_CREATE`는 위 자체 주문서 상품 조회와 구분한다. 기존 상품이나 운영 가격을 임의로 덮어쓰지 않는다.
4. 초대장 생성 때 `{TAESAN_DATA}/invitations/{job_id}/{price}.order.json`에 상품과 행사 조건을 저장한다. 같은 폴더에 가격별 초대장 HTML, 썸네일, 결과 파일을 보존한다.
5. 고객은 `/i/{job_id}/{price}/order`로 이동한다. 없는 주문서는 404, 주문 가능 행사 시간이 지난 경우 410 안내를 유지한다.

이미 발급한 초대장과 주문 조건은 상품 원본을 나중에 수정하더라도 바꾸지 않는다. 가격·옵션·행사 정보는 생성 당시 스냅샷을 기준으로 한다.

### B. 족자 그림을 레이어로 합성한다

공용 `checkout.render()`와 `checkout.html`을 재사용한다. 신랑신부 사진이 있는 상품에서 `#wreath-preview`를 구성한다.

- 바탕: `/checkout-art/sunflower-easel.webp`
- 족자 종이: `/checkout-art/scroll-paper.webp`
- 신랑신부 사진: 주문 스냅샷의 HTTPS `wedding_photo`
- 사진 위치: 유효한 `wedding_crop`이 있으면 `object-position`에 적용하고, 없으면 사진이 잘리지 않는 기본 표시를 사용
- 중량: `/checkout-art/rice-10kg.webp`, `rice-20kg.webp`, `rice-30kg.webp`
- 문구: `#scroll-greeting`
- 보내는 분: `#scroll-sender`

사진이 없는 경우 원본 상품 사진 표시를 유지하고 다른 커플 사진을 임의로 넣지 않는다. CSS 비율·좌표는 현재 원본 이미지에 맞춘 상대 배치다. 디자인 자산을 교체하면 각 레이어 영역도 다시 맞춘다. 화면 비율을 실물 출력 mm 규격으로 추정해 제작 파일에 적용하지 않는다.

### C. 입력을 즉시 반영하고 모바일 넘침을 막는다

1. 옵션 값에는 서버가 만든 `data-amount`, `data-greeting`, `data-kg`, `data-custom`을 사용한다. 옵션 순서를 고정 가정하지 말고 상품 그룹 의미에 따라 처리한다.
2. 추천 문구 선택 시 번호 접두어를 제외한 문장을 표시한다. 직접 입력이면 고객 입력값을 표시한다.
3. 중량 선택 시 해당 중량 이미지를 바꾸고 대체 텍스트도 갱신한다.
4. 보내는 분 입력은 우선 그대로 보여준다. `/checkout-sender` 보조 요청의 응답으로 조직·이름 등의 표시 구조를 다듬되, 요청 실패 시에도 입력한 글자는 남긴다. 지연된 응답이 최신 입력을 덮어쓰지 않도록 요청 취소와 입력값 비교를 유지한다.
5. 문자열을 HTML로 삽입하지 않는다. 서버 HTML 이스케이프와 브라우저 `textContent`를 사용한다.
6. 글자 배치는 실제 렌더링 크기와 영역 높이를 측정해 줄바꿈·글자 크기를 맞춘다. 긴 문구, 긴 단체명, 공백 없는 문장도 족자 밖으로 넘치지 않게 한다.
7. ‘보내시는 분과 같음’을 켜면 주문자 이름이 연동된다. 서버도 체크값에 따라 보내는 분을 사용하며 브라우저 값만 신뢰하지 않는다.
8. 모바일 선택 UI와 미리보기 확대 동작을 유지하고 375~390px 및 PC 화면에서 가로 넘침과 읽기 가능 여부를 확인한다.

### D. 주문 저장과 결제를 서버 기준으로 처리한다

- 고객 입력: 옵션, 보내는 분, 직접 입력 문구, 주문자, 휴대폰, 개인정보 동의. 설치 정보는 행사 스냅샷과 해당 경로의 입력 정책을 따른다.
- 서버 검증: 상품 스냅샷에 실제 존재하는 선택지만 허용하고 기본가와 추가금을 다시 계산한다. 클라이언트 합계금액은 결제 근거로 쓰지 않는다.
- 주문번호: 32자리 16진수 고유 시도 번호를 사용한다. 같은 시도의 반복 제출은 새 결제를 중복 요청하지 않도록 기존 처리와 충돌 검증을 유지한다.
- 저장: `{TAESAN_DATA}/state.sqlite3`의 `invitation_orders`에 정규화된 입력, 금액, 행사 정보, 상품 스냅샷, 사진 표시 정보를 보관한다. 관리자와 제작·배송 후속 업무도 같은 주문번호를 사용한다.
- 결제: 기존 페이앱 어댑터와 `/invitation-orders/payapp` 통보를 재사용한다. 브라우저 성공 화면만으로 승인 처리하지 않는다.
- 결과 불명: 타임아웃 후 새 결제를 자동 요청하지 않는다. 결제번호·서버 금액을 대조하고 중복·역순·부분취소 통보를 기존 규칙대로 처리한다.
- 공개 초대장 폴더에는 주문자 개인정보를 새로 쓰지 않는다. 고객 상태 링크와 관리자/직원 권한 링크를 분리한다.

`INVITATION_CHECKOUT_ENABLED`와 기존 가맹점 설정을 재사용한다. `SHOP_CHECKOUT_ENABLED`를 켰다고 기존 초대장 결제까지 활성화된 것으로 취급하지 않는다. 운영 비밀값을 저장소에 기록하지 않는다.

### E. 저장 보존과 제작·카톡 연결을 구분한다

기존 Render 서비스의 `TAESAN_DATA=/var/data`는 운영자가 확인했고, 조회한 영구 디스크 마운트와 일치한다. 실제 DB·초대장 파일 검사와 운영 백업·복구는 별도로 확인한다. 경로 점검을 위해 새 DB를 만들거나 원본을 덮어쓰지 않는다.

입력 중 족자가 바뀌는 것만으로 인쇄용 PNG/PDF 생성이나 제작 접수가 완료된 것은 아니다. 실제 제작은 결제 확인과 제작 파일 검수 조건을 통과한 주문만 접수하고 중복 실행하지 않는다.

직원·고객 알림은 카카오 알림톡과 샘플 이미지 확인 링크를 사용한다. 문자·MMS 대체 발송은 사용하지 않는다. 페이앱의 일반 주문/배송 메시징 API 지원은 확인 중이고, SOLAPI 계정은 현재 없다. 발송 업체·승인 템플릿이 연결되기 전에는 실제 발송 완료로 보고하지 않는다.

## 4. 필수 검증과 완료 기준

| 시나리오 | 완료 기준 |
|---|---|
| 행사·가격 연결 | 두 가격의 초대장에서 맞는 행사·상품·설치 정보와 금액 표시 |
| 조건 보존 | 원본 상품 수정 뒤에도 기존 초대장과 기존 주문 스냅샷 유지 |
| 문구·보내는 분 | 추천/직접 입력과 보내는 분을 변경하면 최신 값이 족자에 반영 |
| 중량 | 10/20/30kg에 맞는 이미지·가격 표시, 서버 계산과 일치 |
| 주문자 복사 | 체크·해제·보내는 분 변경 뒤 의도한 값 유지, 서버도 동일하게 처리 |
| 모바일 | 긴 문구·긴 이름·공백 없는 입력이 족자 밖으로 넘치지 않음 |
| 보조 요청 실패 | 보내는 분 정리 요청 실패·지연 시 입력 보존, 최신 값 역전 없음 |
| 주문 무결성 | 금액·옵션 조작 거부, 반복 제출·결과 불명에 새 결제 중복 요청 없음 |
| 결제 통보 | 모의 승인·중복·부분취소·전체취소·역순 상태를 주문번호로 대조 |
| 보존·복구 | 독립 환경에서 재시작·백업·복구 후 DB·초대장 파일과 조건 보존 |
| 기존 기능 | 기존 고객 링크·초대장 조회·직원 승인 경로 유지 |

검증은 독립 테스트 데이터와 모의 결제로 먼저 수행한다. 실제 제공된 고객 링크는 읽기와 가상 입력만 확인하고 주문 제출·결제를 실행하지 않는다. 실가맹점 시험과 운영 병합은 별도 승인 범위로 진행한다.

## 5. 현재 확인한 범위와 인계 보고

2026-11-15 제공된 기존 초대장 주문 링크가 HTTP 200으로 열리는 것을 확인했다. 390px 브라우저에서 가상 직접 문구·보내는 분이 족자에 반영되고, 30kg 이미지와 주문자 복사가 동작하며 가로 넘침이 없었다. 이 확인에서는 GET 외 요청을 차단했으므로 보내는 분 서버 정리 응답과 실제 주문·결제는 검증하지 않았다. 이는 모든 길이의 문구 또는 인쇄 품질을 보장하는 결과가 아니다.

완료 보고에는 PR 링크, 코드 커밋과 배포 커밋, 확인 가능한 주문 샘플 링크, 모바일·PC 결과, 금액·중복 결제·취소·보존 검증, 모의/실제 구분, 남은 계정 설정을 적는다. 발견 오류는 수정 후 동일 시나리오로 재확인한다.
