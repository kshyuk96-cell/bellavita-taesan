# 운영 준비와 외부 백업 (2026-11-14)

## 관리자 업무별 배치

주문·결제 → 상품·판매 링크 → 배정·배송 → 정산·집계 → 운영 설정 순서로 기존 기능을 배치했다. 상단 고정 바로가기를 제공하며 폼 action과 서명·권한은 유지한다. 기존 정정·제작 검수·AS·CSV 배정·배송 사진 업무를 제거하지 않는다.

운영 설정의 연결 준비 화면은 실제 값을 표시하지 않고 아래 준비 상태를 알려준다. 가짜 검증 키가 들어 있다는 이유로 실가맹점 설정 완료로 표시하지 않는다.

## 페이앱 제한된 실제 테스트 준비

실거래는 이번 작업에서 실행·활성화하지 않는다. 검증 서버는 모의 어댑터를 강제 사용한다.

1. 가맹점에서 제공하는 테스트 결제 수단/계정과 허용 금액·취소 범위를 확인한다.
2. 독립적인 실가맹점 검증 환경에 USER_ID/LINK_KEY/LINK_VALUE/REQUEST_KEY를 비밀 설정으로 등록한다. 현재 모의 서버에 운영 키를 복사하지 않는다.
3. 결제 요청은 서버 계산 금액·고유 주문번호를 사용하고 통보 HTTPS 경로는 /invitation-orders/payapp이다. 성공 화면 이동과 승인 통보를 구분한다.
4. 승인·통보 재전송·중복·부분취소(원거래 번호/원금액)·승인취소·역순 통보를 거래번호로 대조한다.
5. 타임아웃이면 페이앱 판매자 거래 현황에서 대조한다. 결과 불명인 주문에 새 결제를 자동 요청하지 않는다.

공식 문서: https://api.payapp.kr/dev_center/dev_center01.html . 모의 검증 통과가 실제 가맹점 테스트 수단 제공이나 계약 권한을 증명하지 않는다.

## 알림톡 설정 점검

필수 항목: SOLAPI_API_KEY, SOLAPI_API_SECRET, SOLAPI_KAKAO_PFID, SHOP_ALIMTALK_TEMPLATE_ID.
신규 주문 채널은 SHOP_MESSAGE_CHANNEL=alimtalk, 발송은 SHOP_MESSAGES_ENABLED 및 SHOP_ALIMTALK_ENABLED를 별도 제어한다. 이번에는 모두 실발송 꺼짐을 유지한다.

승인받을 알림 예시:

> [벨라비타] #{상태}
> 주문번호: #{주문번호}
> 상품: #{상품명}
> 입력 문구 이미지 확인: #{샘플링크}
> 주문·배송 확인: #{주문링크}

주문 확인·배송 중·배송 완료·부분취소·전체취소의 상태별 템플릿을 승인받거나, 해당 변수를 허용한 공통 승인 템플릿을 사용한다. 선택 설정은 SHOP_ALIMTALK_TEMPLATE_CONFIRMED/SHIPPING/DELIVERED/REFUND/CANCEL이다. 템플릿 승인 상태와 발신 채널 소유/권한은 실제 계정에서 확인해야 한다.

알림톡은 주문별 문구 이미지를 확인하는 링크를 보낸다. 실제 동적 이미지 파일 첨부는 기존 MMS 채널 기능과 구분한다. 문자 대체 발송은 끈다. 직원 수신자는 관리자 직원 알림 번호 설정에서 관리하며 고객과 같은 단말에는 같은 이벤트를 중복 발송하지 않는다.

## 현금영수증 설정 점검

- SHOP_CASH_RECEIPT_ENABLED는 이번에 0 유지.
- 발급 주체 SHOP_CASH_RECEIPT_OWNER=shop 여부와 페이앱 자체 자동 발급의 중복 가능성을 확인한다.
- 관리자에서 상품별 TG01 과세 / TG02 면세를 실제 취급 상품 기준으로 확정한다. 임의로 과세 구분을 채우지 않는다.
- 승인 통보의 결제수단 6/7(계좌이체/가상계좌), 승인 시각, 고객 발급 식별자를 대조한다. 카드나 결제사 발급 내역을 별도 중복 발급하지 않는다.
- 발급·취소·부분취소 정정, 실패·결과 불명 대조 후 재처리는 기존 어댑터를 사용한다. 설정 변경은 기존 주문 스냅샷의 과세 구분을 덮어쓰지 않는다.

## 외부 백업

Google Drive 폴더: (비공개 백업 위치는 서버 설정과 관리자 검증 기록에서 확인)

검증 서버의 인증된 내보내기에서 SQLite·파일 체크섬·복구 검증을 마친 스냅샷을 AES-256-GCM으로 암호화한다. 암호화 키는 검증 서비스 SHOP_BACKUP_ENCRYPTION_KEY에만 보관하고 저장소·백업 파일·로그에 넣지 않는다. 복구 키는 서버와 별개로 운영자가 관리해야 하며, 키를 잃으면 암호화 파일을 복구할 수 없다.

연결된 Drive 앱을 통한 저장 → 원본 바이트 재다운로드 → 체크섬 비교 → 복호화·새 임시 경로 복구 검증과, 서버의 매일 자동 업로드는 구분한다.

서버 자동 업로드 설정:
- SHOP_EXTERNAL_BACKUP_ENABLED=1 (이번에는 0 유지)
- SHOP_BACKUP_DRIVE_FOLDER: 검증 전용 비공개 폴더 ID
- SHOP_BACKUP_DRIVE_CREDENTIALS: 해당 폴더에만 권한을 부여한 별도 서비스 계정 파일
- SHOP_BACKUP_ENCRYPTION_KEY: 32바이트 키의 64자리 16진수 문자열

현재 서버 업로드용 서비스 계정은 미연결이다. 연결된 ChatGPT Drive 앱의 인증을 Render로 복사하지 않는다. 자동 업로드 어댑터는 업로드한 암호화 파일을 재다운로드하여 체크섬과 복구까지 확인한 경우에만 verified로 기록한다. 외부 전송 실패가 로컬 백업 성공을 지우지 않으며 이전 백업을 삭제하지 않는다.

단일 백업 원본·암호문/복구 한도는 64MB이다. 초과 시 분할/스트리밍 구성을 먼저 확장해야 한다. 원본을 덮어쓰는 복구는 허용하지 않는다.

오프라인 복구:
```
python external_backups.py restore --file downloaded.bvbackup --destination /새/복구/디렉터리
```
키는 비밀 환경변수나 화면에 표시되지 않는 입력으로 제공한다. 명령 인수나 저장소 파일에 넣지 않는다.

Drive 백업 파일: (비공개 백업 위치는 서버 설정과 관리자 검증 기록에서 확인)
비공개 64,513바이트 암호화 파일을 저장하고 원본 바이트 재다운로드, SHA-256 비교, 실제 Render에서 복호화·임시 경로 복구를 확인했다. 기존 주문 3건·상품 4개와 무결성 검사가 통과했고 검증 이력을 관리자에 기록했다. 원본 DB를 덮어쓰지 않았다.

실가맹점 키와 알림톡 4개 필수 설정·승인 템플릿·직원 번호, 4개 상품의 과세/면세 구분은 미확정으로 표시한다. 설정 완료로 가정해 실제 성공을 꾸미지 않는다. 실거래·실발송·국세청 발급은 실행하지 않았다.

서버의 자동 업로드 인증은 미연결이고 이번 외부 저장은 연결된 Drive 앱을 통한 수동 검증이다. 개인 My Drive의 무인 자동화에는 사용자 OAuth 등 쓰기·저장 용량 권한이 있는 별도 서버 인증이 필요하며, 서비스 계정에 폴더만 공유하는 것으로 충분하다고 가정하지 않는다. 공유 드라이브를 사용하는 경우에도 권한·API 옵션을 실제 계정에서 검증한 뒤 활성화한다.

발견 오류: 준비 화면에서 직원 번호 테이블의 컬럼을 잘못 참조한 오류를 기존 order_ops.phones 조회로 수정하고 같은 관리자 경로를 재검증했다. 시스템 Python에 google-auth가 없어 실패한 추가 테스트는 requirements가 설치된 프로젝트 .venv 환경에서 다시 실행해 전체 통과했다.
