# 승인된 첫 20개 개발 묶음: 데이터 준비와 핵심 통합시험 기반

사용자가 승인한 첫 20개만 구현했다. 고객 서비스의 기능 개발·인수 완료와 구분한다. 이번 구현은 테스트 데이터 수신 계약과 **전용 로컬 참조 서버**이며, 기존 고객 사이트에 seed 권한이나 운영 DB 접근을 추가하지 않았다.

현재 고객 검수 서버는 `isolated_server_review`와 카드 simulator를 제공하지만 `hope-test-lab/v1` 데이터 주입 프로토콜을 광고하지 않는다. 지정 데이터 U04/P02/U09를 임의의 기존 API로 주입하거나 기본 샘플로 대체하지 않는다. 원격 연결은 차단하고, 서버 어댑터의 구현·로컬 HTTP 통합 검증을 먼저 완료한다.

## 실행과 산출물

```bash
python -m unittest manager_bridge.tests.test_hope_batch01 -q
python scripts/run_hope_batch01.py --output /tmp/hope-batch01

# 기존 검수 서버에는 상태 GET만 수행한다. 임의 seed POST는 하지 않는다.
python scripts/run_hope_batch01.py --output /tmp/hope-batch01 \
  --review-token-file /private/hope-review.token
```

실행 소스를 먼저 커밋해야 한다. CLI는 실행 전·후 파일 해시와 HEAD를 대조한다. 전용 임시 SQLite와 loopback 서버를 만들고 종료 시 닫는다. raw 역할 토큰은 메모리에만 있으며 DB에는 hash만 저장한다. 인증 헤더·토큰·개인정보·실제 카드번호는 증거로 내보내지 않는다.

- `batch-summary.json`: 승인 20개 기대/실제/판정·source·원격 준비 상태·합성 자료 접수 판정.
- `local-evidence.json.gz`: workspace별 초기 상태 해시, 최종 상태, 요청 ID·역할·원거래·역분개·세대별 전체 증거.
- `local-common-report.json.gz`, `local-trusted-contract.json.gz`: 기존 공통 QA schema와 사전 계약. 인수는 **로컬 참조 어댑터의 개발 검증**만 뜻한다.
- `customer-report.docx/.xlsx/.json`: 고객 양식 38개는 로컬 참조 결과로 PASS 처리하지 않는다. 대상 배포 소스를 모르면 `null/미확인`으로 남기며 테스트 엔진 SHA로 대신 채우지 않는다. 별도 “개발묶음20/로컬거래증거” 표를 추가한다.
- 기존 고객 결함은 `OPEN_NOT_RETESTED`로 유지한다. 이번 결과만으로 기존 S1/S2를 해소하거나 재시험했다고 쓰지 않는다.
- `SHA256SUMS`: artifact 손상 검사이며 승인 주체·독립 관찰을 인증하는 서명이 아니다.

## 전용 데이터 DB와 실행 안전성

기존 비즈니스 DB, 기존 빈 DB, marker/테이블이 다른 DB, 공개 권한 파일, symlink를 열지 않는다. fixture DB만 seed/reset한다. 회원은 본인 원장·예약만 조회하고 상품관리자는 상품만 조회한다. 재무가 초기화를 하거나 회원이 환불을 실행할 수 없다.

모든 변경은 SQLite `BEGIN IMMEDIATE` 트랜잭션이다. `(workspace,generation,request_key)`가 작업 중복을 차단하고 다른 actor/내용으로 키를 재사용하면 거절한다. 재시작 후 같은 성공 요청은 저장된 receipt를 반환한다. 이전 세대 요청은 차단하며 초기화 전 상태와 이벤트를 보존한다. 불명 결제가 남아 있으면 초기화도 거절한다. 실제 효과를 자동 추정하거나 동일 결제를 다시 보내지 않는다.

최대 workspace 1000개, 세대 100개, 계약별 명령 1~1000회(기본 200), 요청 64KiB, 응답 4MiB, HTTP timeout 5초로 제한한다. raw HTTP 오류·secret을 출력하지 않는다. 명령은 고정 enum과 허용 필드만 받는다. 외부 명령·모듈·SQL·PAN/CVC를 실행/저장하는 경로는 없다.

## 재무 검증과 정책 경계

opening 원금/보너스/특별포인트도 합성 원거래를 가진다. 거래 이후 `원금 잔액 = 원금 발생 - 사용 - 기반환 - 확정차감`, bucket별 journal 합계, 객실 재고 합계를 검증한다. 취소는 원 사용 journal을 참조하는 역분개를 추가하고 기존 기록을 고치지 않는다. 탈퇴는 무상 BP를 반환금에 합산하지 않는다. 무상 포인트 잔여 처리 정책은 대기로 표시한다.

참조 서버 계산은 Decimal로 구현하고 기대값은 별도 고객 계약/정수 오라클에서 만든다. 예제 계약 `example_bonus_order='BP_SP'`, 수수료 0원은 **고객 문서의 합성 예제 재현**에만 사용한다. `operational_policy_approved`는 항상 false다. 기본 계약은 BP/SP·취소 규칙 미확정 상태다. CP·자격 중지 반환·비영(非零) 수수료를 임의 확정하지 않는다.

분할청구 항목은 데이터와 계산된 예약금·잔금·납기를 준비한다. 참조 서버의 purchase는 `full_simulator_payment`로 표시하며 실제 예약금/잔금 각각의 카드 승인을 검증했다고 주장하지 않는다. 실제 PG 빌링키 해지나 은행 환불도 수행하지 않는다.

## 실제 고객 서비스 연결 상태

이 코드가 고객 서비스의 결제/원장 구현을 대체하지 않는다. 원격 검수 API가 새 프로토콜을 광고하더라도 승인된 실제 어댑터 바인딩이 없으면 자동 연결하지 않는다. 호스트·토큰을 임의 추정하거나 운영 테이블에 seed하지 않는다.

이번 20개 구현은 로컬 테스트 어댑터와 통합시험 기반이다. 고객 서비스의 실제 source adapter·검수 전용 seed 수신부·승인된 격리 호스트·화면 증거·PG 테스트 연결이 다음 통합 단계에 남는다. 고객 인수 38개 및 기존 서비스 결함은 별도로 재시험해야 한다. 운영 배포나 유료 자원 생성은 이 묶음에서 하지 않는다.
