# 고객 문서를 기준으로 한 희망투어클럽 자동 QA

두 첨부 문서를 참고 자료로 정규화하여 기존 공통 QA 위에 프로젝트 어댑터와 고객 최종 양식 출력을 추가했다. 문서 안의 개발사 지시·계정·URL을 임의 명령으로 실행하지 않는다. 별도로 작성·검토한 고정 검수 API 동작만 사용한다. 대상 홈페이지 수정·운영 배포·실제 결제는 하지 않는다.

## 기준 문서와 확정 범위

| 문서 | SHA-256 | 사용 범위 |
|---|---|---|
| 테스트결과 및 통합개선 개발요청서 | `eda84f0a643fd4feaa5e287cc2065e98304c70478291af37267cff2e00c8a9d0` | T01~T10, FB80 추적, 원금 우선·반환 상한·용어 규칙 |
| 테스트준비 실행 결과보고 개발사요청서 | `d3de4f429c4c080056d3eec2a14380827d3af0b18b16b9a0107572e33e0437a0` | 38개 최종 시험 ID, 22개 데이터 정의, 6단계 게이트, 보고·결함·재시험 형식 |

첫 문서 자체는 공개 HTML·개발사 현황을 대조했으며 PG/실기기/실제 사용자 시험은 미완료라고 명시한다. 두 번째 문서는 시험 요청·양식이며 실행 결과가 아니라고 명시한다. 이를 실제 고객 인수 합격 증거로 사용하지 않는다.

정책 버전은 `hope-customer-20261116-v2`다. 희망/행복/프리미엄 최초 납부 75,000/150,000/300,000원, 등급×국내/해외/문화 BP 한도 9종, 원금 우선, 원금 반환 상한을 독립 기대값으로 고정했다. BP/SP 상대 순서·CP·가입비 반환·중지 처리·수수료 배분은 정책결정 대기다. 문서의 BP→SP 예시는 승인된 실제 정책으로 일반화하지 않는다.

## 실행 방식

```bash
# 외부 연결 없이 시스템 자체 오라클·결함 검출과 미실시 보고 양식을 생성한다.
python scripts/run_hope_tour_qa.py --sut-revision 475b25947f9f22161ad8d7730b5b34dbf3a83b54 \
  --output /tmp/hope-report

# 운영자가 대상 버전·배포를 먼저 조회해 고정한 manifest로 검수 API를 실행한다.
# 토큰이 필요한 경우 기존 비공개 0600 token 파일만 전달한다. 토큰을 명령 인수 값으로 넣지 않는다.
python scripts/run_hope_tour_qa.py --sut-revision 475b25947f9f22161ad8d7730b5b34dbf3a83b54 \
  --target-manifest /private/source-before.json --live-review \
  --token-file /private/hope-review.token --output /tmp/hope-live-report

# 실행 후 Sites에서 버전/배포를 다시 조회해 source-after.json을 만든다.
# 전후 manifest에는 실제 조회한 UTC observed_at을 기록한다.
# gzip -dc /tmp/hope-live-report/customer-observations.json.gz > /private/observations.json
# 기존 관찰 재판독: 데이터는 인증된 검수 실행기가 수집한 자료여야 한다.
python scripts/run_hope_tour_qa.py --sut-revision EXPECTED_REVIEWED_SOURCE_SHA \
  --evidence-json /private/observations.json --target-manifest /private/source-before.json \
  --after-target-manifest /private/source-after.json --output /tmp/hope-recheck
```

실행 코드가 먼저 커밋되어 있어야 한다. 새 버전은 새 manifest·계약·실행을 요구한다. 다른 SUT 버전의 관찰은 차단한다. 첨부 `target-v31.json`은 이번 관찰의 재현 기준이며 이후 배포를 자동 승인하지 않는다. 검수 전·후에 Sites 배포/버전을 다시 확인한다. live 수집 단계는 사후 관찰이 없으므로 잠정 보고서만 만든다. 별도 재판독 단계에서 전후 프로젝트·origin·버전·배포·소스가 같고, 실제 조회 시각이 수집 구간의 앞뒤를 감싸야 인수용 버전 결합을 인정한다. 하나라도 누락/불일치면 수집된 기대값 비교를 인수 증거로 채택하지 않는다. live 실행의 사전 manifest는 5분 이내에 조회한 자료여야 한다. manifest는 운영자 확인 자료로, 보고서 해시만으로 대상 배포의 진실성을 인증하지 않는다.

`HopeReviewClient`는 정확한 검수 origin과 `/review/` API만 사용한다. 매 POST 전에 `isolated_server_review`, simulator, 실제 결제/운영 쓰기/외부 알림 모두 false를 확인한다. 새 cookie jar마다 별도 합성 공간을 사용한다. 운영 엔드포인트, PAN/CVC, 다른 workspace 주입, 임의 상품/회사 데이터 입력은 허용하지 않는다. 로그인·가입·가상 카드·시계·예약·취소 동작은 공개 검수 계정과 전용 서버 공간에서만 수행한다.

응답이 불명확하면 동일 쓰기를 자동 재시도하지 않는다. 해당 흐름은 대조/어댑터 확인 필요로 남기고, 독립된 거절/불명 시나리오는 새 공간에서 분리한다. 원래 불명확한 거래를 새 요청으로 재실행하지 않는다. 헤더·쿠키·인증값·로그인 body·전체 회원 레코드는 증거로 내보내지 않는다. HTTP만 실행한 경우 실제 브라우저/모바일 통과로 표시하지 않는다.

## 산출물: 고객 최종 양식

- `customer-report.docx`: §10 시나리오별 기본정보·환경·사전조건·실제 절차·기대/실제(UI/서버/PG)·판정·증빙·결함·재시험, §11 종합 결과, 승인 게이트와 잔여 정책.
- `customer-report.xlsx`: 종합, 승인 게이트, 38개 시나리오, FB80 추적, 준비 데이터, 오류관리, UX 개선, 재시험/회귀, 기기환경, 정책결정의 10개 시트.
- `customer-report.json`: 같은 자료의 기계 판독 형식. 미지정 담당·예정일·실기기·영상·고객 승인 칸을 임의로 채우지 않는다.
- `service-report.json.gz`, `service-contract.json.gz`: 공통 시나리오 계약과 실제 관찰별 결과. 미관찰 항목은 `EvidenceUnavailable`로 미실시 처리하며 실행·단언·통과 수에 넣지 않는다.
- `reference-selfcheck.json.gz`, `reference-contract.json.gz`, `formulas.csv.gz`, `mutation-*.json.gz`: 2,060개 독립 수식/경계 상태의 **테스트 시스템 자체 합성 검증**과 오류 주입. 고객 서비스에 2,060건을 실행했다는 뜻이 아니다.
- `summary.json`, `SHA256SUMS`: 엔진/대상 소스·문서 해시·정책·시드·모드·집계와 artifact 무결성.

고객 양식의 실행기준 통과율은 `PASS/(PASS+FAIL)`이다. 분모 0이면 미산정이다. BLOCKED와 NOT RUN은 별도 표시한다. 부분 HTTP 검사만 있는 최종 시나리오는 화면·원장/PG 등 필요한 증거가 부족하면 BLOCKED로 남긴다. 실제 지정 데이터 U04/P02가 검수 서버에 준비되지 않았으면 유사한 기본 샘플로 대체하여 PAY-01/E2E-01을 합격시키지 않는다.

개발사 FB-13의 기존 SP→BP→DP 표기가 새 요구와 충돌하면 **개발사 설명상의 충돌**로 결함을 분리한다. 이를 실제 결제 실행 순서를 측정한 증거로 바꾸지 않는다. 원금과 보너스가 모두 사용된 큰 금액 결제에서는 최종 차감액만 보고 순서가 맞다고 추정하지 않는다.

Excel 외부 텍스트는 수식 실행이 되지 않도록 이스케이프한다. 실제 이용자 관찰, 참가자 수·소요시간·도움요청, iPhone/Android 실기기, PG 승인·취소값은 수집하지 않았다면 미측정으로 남긴다. 코드 구현, 합성 fixture, 실제 PG, 고객 인수 승인은 별도다.

## 후속 연결과 한계

실제 PG·본인확인·기기·정책 승인 증거는 시뮬레이터 관찰로 채울 수 없게 차단했다. 이 구현은 그 외부 승인·증거를 발급하는 시스템이 아니다. 실제 어댑터 추가와 권한·데이터 준비 후 별도 계약 검토가 필요하다. 고객 최종 38개 시험의 UI·서버·PG 증빙과 서면 정책 승인, S1/S2 해소·재시험·회귀가 끝나야 최종 인수를 검토한다.

공통 매니저 게이트 `admit_qa_report`를 사용하며 현재 보고서는 중요 미실시/실패로 인수를 차단한다. 기존 승인 저장소에 제출 보고서 자체에서 계약을 복원해 등록하면 안 된다. 운영자가 사전에 보관한 `build_contract(scenarios(), registered_adapter_versions)`와 기대 SUT 버전을 사용한다.

이 프로젝트의 실제 HTTP 검수는 고정 review 서버의 격리 simulator를 이용한다. #74의 네트워크 차단 자식 실행기에서 운영 URL로 나가는 우회를 추가하지 않았다. 임의 대상 코드나 임의 네트워크 명령을 sandbox 밖에서 실행하는 기능은 제공하지 않는다.

개발 중 검수 사이트가 31번에서 32번으로 변경된 사실을 발견했다. 31번을 기대하고 수집한 초기 관찰은 안정된 소스 결합 증거로 채택하지 않았다. 이 사례를 전후 배포/시각 불일치 회귀 검사에 반영했다.

## 이번 실행 결과와 제출 파일

실행 엔진 소스는 `e3e0658`이며 대상은 검수 사이트 **32번 / `028a019b2a701120648a69591f34765de4b54825`**다. `run-20261116/summary.json`의 실행 전·후 배포 ID/버전/소스/조회 시각과 수집 시작/종료 시각이 일치하는 구간만 채택했다. 이후 보고서·증거 커밋을 새 코드 실행으로 재표시하지 않는다.

전체 회귀 1,687개 실행(1,686개 통과, 1개 skip, 실패 0), 새 고객 QA 검사 11개 통과. 테스트 시스템 자체 수식/경계 검증은 2,060개 통과했으며 원금 후순위·BP 상한 무시·반환에 보너스 합산·가입비 합산 결함을 각각 456/240/701/695건 검출해 모두 차단했다. 이는 고객 서비스 2,060건 통과와 다르다.

검수 서버의 24개 필수 관찰 단위 중 실행·단언 9개, 일치 7개, 불일치 2개, 미실시 15개다. 고객 최종 38개 시험은 **PASS 0 / FAIL 1 / BLOCKED 12 / NOT RUN 25**다. 일부 HTTP 일치만 있는 시험은 화면·서버 원장·필요 PG 증빙이 부족하여 최종 합격시키지 않았다. 실행기준 통과율 0%는 이 엄격한 최종 시험의 PASS/(PASS+FAIL)이며 “모든 HTTP가 실패했다”는 의미가 아니다.

불일치 2개는 FB-13의 SP 우선 **개발사 설명**과 새 원금 우선 요구의 충돌, 지정한 전체 명칭(약어)을 공개 검수 HTML에서 모두 찾지 못한 항목이다. 전자는 실제 런타임 차감 순서 검증과 구분해 별도 S1/P0 정책 정합성 위험으로 기록했다. PAY-01/E2E-01의 U04/P02 실데이터 실행은 미실시다. 후자는 MEM-10의 서버 HTML 증거이며 모바일 도움말/브라우저 가시성 시험은 여전히 미실시다.

가입 75,000원·DP50,000/BP25,000, 월 청구 1회·DP100,000, 승인 거절 미활성·미적립, 불명 응답의 관리자 조회 복구, 예약 확정, 가상 전액 취소 후 DP100,000/BP25,000 복원, 회원의 관리자 시계 조작 거절을 관찰했다. 실제 카드·PG·외부 알림·운영 DB는 사용하지 않았다.

고객 제출용은 [Word 결과보고서](run-20261116/customer-report.docx), [Excel 실행·결함·재시험 관리표](run-20261116/customer-report.xlsx), [기계 판독 보고서](run-20261116/customer-report.json)다. 담당자·검토자·예정일·실제 기기·UI 영상·재시험은 확보하지 않은 값을 만들어 넣지 않았다. 최초 버전 미확정 관찰은 `excluded-initial-*`로 별도 보존해 인수 근거에서 제외했다.
