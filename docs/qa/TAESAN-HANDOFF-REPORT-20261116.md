## 1. 요약

기존 합성 QA를 이어받아 관리자가 사전 승인한 계약으로 작업을 접수하고, 작업자가 결과를 제출하고, 관리기가 결과와 인수 판정을 회수하도록 구현했다. 사전 지정한 개발 작업은 현재 후보 소스에 대한 QA 통과 증거가 없으면 기존 관리자 검토와 3단계 기술 인수에서 차단한다.

중복 실행, 중요 항목 미검증, 필수 커버리지 누락, 소스·작업 불일치, 중요도 하향을 차단했다. 불확실하거나 시간이 만료된 실행은 자동 재시도하지 않는다. 실제 저장소의 주문 정규화 함수까지 오프라인으로 검사했고, 그 결과를 로컬 관리기 HTTP에 제출해 기존 개발 작업의 인수까지 연결하는 재현 절차를 실행했다.

**배포된 비운영 서비스·실제 관리기·승인된 격리 실행기 연결은 미완료다.** 이 보고서는 실제 고객 서비스, UI, 주문 시트 저장, 결제·정산 정책, 운영 배포가 검증됐다는 보고가 아니다.

각 항목의 영향·발생 가능성·복구 난이도는 사전 계약과 시나리오 증거에 있다. 계약 안의 미검증 0은 서비스 전체의 미검증 0을 뜻하지 않는다. 위 두 실행은 아래에 명시한 각 소스 버전의 결과로 관리하며 합산해 전수 검증으로 표현하지 않는다.

## 4. 시나리오 상세와 관리기 연결 증거

`run-20261116-followup/scenarios.json.gz`와 `order-ledger.json.gz`에 입력·기대값·실제값·판정·증거를 보존했다. `manager-handoff-rehearsal.json.gz`에는 최신 연결 재현의 제출 보고서 전체와 관리기 판정이 있다. 요약은 `manager-handoff-summary.json`이다.

| 관리기 HTTP 재현 항목 | 관찰 결과 |
|---|---|
| QA 증거 없이 기존 개발 작업 검토 | HTTP 409, 인수 차단 |
| 실제 주문 함수 288건 통과 결과 제출 | `accepted`, GET 회수 결과와 동일 |
| 완료 작업 실행권 재요청 | HTTP 409, 재실행 차단 |
| P1 항목을 미검증으로 제출 | `critical_scenario_not_passed`, 차단 |
| 필수 커버리지 삭제 | `required_coverage_missing`, 차단 |
| 과거/다른 후보 소스 제출 | `source_revision_mismatch`, 차단 |
| 다른 작업의 결과 재사용 | `job_binding_mismatch`, 차단 |
| P1을 P3으로 낮추고 보고서 해시 재계산 | `trusted_scenario_contract_mismatch`, 차단 |
| 현재 후보의 통과 QA를 제출한 뒤 기존 작업 검토 | `reviewed` 도달 |

위 9개 관찰을 실제 loopback HTTP와 임시 SQLite로 재현했다. 코드가 HTTP 성공 응답을 받았다는 사실만으로 통과 처리하지 않고, 기대 상태·차단 사유·회수된 결과·기존 작업 상태를 단언한다. `reviewed`는 관리자 기술 검토 기록이며 운영 승인이 아니다.

## 5. 계산식 보고서

필수 수식 1,000건의 계약·변수·단위·반올림·기대/실제 결과는 `formulas.csv.gz`에 있다. 대상 Decimal 계산과 독립 정수 오라클을 대조한다. 금액 절사 결함을 주입했을 때 270건 실패를 검출했다.

이는 기존 가상 견적 계약이다. 실제 서비스 할인·세금·정산의 적용 조건, 계산 순서, 업무 근거와 승인 상태는 확정되지 않았다. 실제 계산식 검증 완료로 인수할 수 없으며 별도 관리자 계약 승인이 필요하다.
