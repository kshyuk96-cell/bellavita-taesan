# 공통 QA 후속 개발: 접수·회수 연결과 실제 코드의 오프라인 검사

## 요약 / 인수 범위

기준 PR #72의 HEAD `1b61986cb88624db6ec8cadfbc9cf4bd92115796`에서 별도 worktree와 `codex/taesan-qa-manager-followup-20261116` 브랜치로 개발했다. 자동 자료 접수는 가능하지만, 전체 완료 조건의 인수는 **보류**한다. 실제 서비스 비운영 서버/관리기 연결 권한과 승인된 실행기 경로가 주어지지 않았다. 실제 주문 시트 저장·UI·결제·문자·고객 자료·운영 배포는 미검증이다.

실제 저장소의 `order_ledger.details_for_sheet`를 외부 연결 없이 검사했다. 이는 가상 정책만 검사한 기존 실행보다 대상이 넓지만, 배포된 스테이징 서비스 검증을 대신하지 않는다. `synthetic_only` 인수 표시는 합성 자료 접수이며 운영 승인이 아니다.

## 접수와 버전 계약

`manager_bridge.qa_jobs.QAJobs`가 기존 인증·프로젝트 접근 제어·SQLite 트랜잭션을 재사용한다.

- 소유자가 `approve()`로 실행 전 검토한 계약, 필수 커버리지, 프로젝트, 후보 40자리 소스 SHA, 어댑터 실행 릴리스, 최대 실행 시간을 고정한다. 승인 ID는 전체 manifest의 digest다. 승인 변경은 새 ID를 만든다. 작업자 HTTP에는 승인 생성/교체 경로가 없다.
- 계약의 `adapter_versions`가 어댑터 이름/버전 등록부다. 호출 가능한 코드는 호스트가 명시적으로 등록한다. 제출한 경로, 명령, Python 문자열은 실행하지 않는다. `adapter_release`는 관리자 검토 실행 환경의 식별자이며 격리를 증명하는 서명이나 자동 설치 명령이 아니다.
- 관리자가 접수한 `task`와 `request_key`를 승인에 결합한다. 같은 키/같은 작업은 기존 작업을 반환하고, 같은 키/다른 작업은 409다. 승인당 최대 10,000개 접수, 계약당 최대 10,000개 시나리오, 결과 최대 32 MiB, 실행권 최대 3,600초다.
- 실행권은 인증된 작업자에게 한 번만 주며 프로젝트당 실행/대조 대기 작업 하나만 허용한다. 다른 작업자가 대신 완료할 수 없다. 버전이 같은 다른 작업에도 보고서를 재사용할 수 없도록 `job_binding` 전체를 대조한다.
- 결과는 기존 `admit_qa_report`를 반드시 거친다. 중요 항목 미통과, 커버리지·수식·위험 계약 변조, 소스·어댑터 버전·작업 결합 불일치이면 `blocked`다. 보고서와 판정을 같이 저장하여 관리기가 회수한다.
- 제한 시간 만료와 실행 중 취소는 `reconciliation_required`다. 자동 재시도·재실행권 발급·자동 해제가 없다. 대기 중 취소만 `cancelled`다. 관리자와 실행기 운영자가 실제 중단·외부 효과를 대조해야 한다. 이번 서버는 실행 프로세스를 소유하지 않으므로 제한 시간이 프로세스를 강제 종료한다는 주장은 하지 않는다.

## HTTP 사용법

기존 `manager_bridge.server`의 Bearer 인증과 프로젝트 권한을 적용한다. API는 코드나 외부 서비스를 실행하지 않는다. 로컬 검사는 임시 DB와 loopback HTTP만 사용한다.

| 요청 | 역할 | 기능 |
|---|---|---|
| `POST /v1/qa/jobs` | owner/manager | `{approval, request_key, task}` 접수 |
| `GET /v1/qa/jobs/{id}` | 프로젝트 owner/manager/worker | 상태·보고서·인수 판정 회수 |
| `POST /v1/qa/jobs/{id}/claim` | worker | `{}`로 한 번의 실행권과 고정 manifest 회수 |
| `POST /v1/qa/jobs/{id}/result` | 실행권 worker | `{report: ...}` 제출; 재검증 후 저장 |
| `POST /v1/qa/jobs/{id}/cancel` | owner/manager | `{}`로 취소 또는 대조 필요 상태 요청 |

소유자는 신뢰된 호스트 코드에서 다음과 같이 승인한다. 아래 계약은 작업자 보고서에서 복원하면 안 된다.

```python
from manager_bridge.qa_jobs import QAJobs
from taesan_core.universal_qa import build_contract
from taesan_core.qa_order_ledger import suite, adapter

jobs = QAJobs(store)
approval = jobs.approve(owner_token, project='bellavita',
    source_revision=reviewed_candidate_sha,
    contract=build_contract(suite(), [adapter()]),
    coverage=['ledger-date-time-channel'],
    adapter_release='reviewed-offline-ledger-v1', max_seconds=300)
# 기존 개발 작업이 pending_approval일 때 QA를 필수 인수 조건으로 고정한다.
jobs.require_for_task(owner_token, development_task_id, approval)
job = jobs.receive(manager_token, approval, 'qa-request-001', development_task_id)
```

실행기는 별도로 승인한 격리 경로에서 고정 버전 어댑터를 실행한다. 결과에 아래 객체를 추가하고 전체 `report_digest`를 다시 계산한 뒤 제출한다. 이 digest는 작업자 인증이나 실행 관찰의 신뢰성을 대신하지 않는다.

```python
report['job_binding'] = dict(project='bellavita', task='development-task-001',
    approval=approval, adapter_release='reviewed-offline-ledger-v1',
    source_revision=reviewed_candidate_sha)
```

## 실행과 증거

```bash
python scripts/run_universal_qa.py --seed 20261116 --output /tmp/universal-qa
python scripts/run_order_ledger_qa.py > /tmp/order-ledger-qa.json
python -m unittest manager_bridge.tests.test_qa_jobs -q
python -m unittest discover -s manager_bridge/tests -t . -q
python -m unittest discover -s taesan_core/tests -t . -q
```

실행 전에 코드가 커밋되어야 한다. 결과는 실행 당시 소스 SHA에 결합하며 이후 문서/증거 커밋 HEAD를 소급 적용하지 않는다. 고정 시드 20261116이다. 기존 3,006건을 두 번 실행하여 생성·실행·단언·통과 3,006, 실패·차단·미검증 0과 결함 주입 검출을 확인했다. 원본 baseline은 인계 HEAD, 새 결과는 후속 실행 SHA에 결합한다. 서로 다른 리비전의 artifact가 동일하다고 주장하지 않는다.

`run-20261116-followup/`에 전체 시나리오·계약·수식 CSV·요약과 실제 주문 정규화 결과를 보존한다. 시나리오별 입력·독립 기대값·실제값·증거는 압축 artifact에 들어 있다. 수식 보고서는 기존의 가상 견적 계약이며 실제 서비스 과금 규칙의 승인을 뜻하지 않는다.

실제 코드 검사 288건은 날짜 9종 × 시각 8종 × 지역 4종의 연결 조합이다. 윤년/연말/빈값/잘못된 날짜 타입, 00:00·23:59·24:00·잘못된 분, 활성 지역·미등록 지역을 검사한다. 기대값 표를 먼저 명시하며 SUT로 정답을 만들지 않는다. 테스트 프로세스의 audit hook가 네트워크·자식 프로세스·파일 쓰기를 거절한다. 이 hook는 임의/악성 어댑터의 OS 격리 경계가 아니다. 현재 관리형 작업 공간의 검토된 코드만 실행했다. 추가 OS 네트워크 namespace 격리는 환경의 UID map 제한으로 사용할 수 없었다.

## 중요도·업무 흐름·계산식·결함

기존 계약의 P0 회사 경계, P1 주문·재시도·견적 계산, P2 정상 입력, P3 가상 진단 분류는 보존했다. 실제 주문 정규화 288건은 P1이며 모든 항목에 영향·가능성·복구 근거가 있다. 개별 등급과 흐름별 상세 결과는 artifact에서 집계할 수 있다. 정상/예외/회귀 입력은 모두 합성 데이터다.

기존 필수 수식 1,000건은 독립 정수 오라클과 Decimal SUT를 대조한다. 수식·변수·단위·반올림·기대/실제 결과는 `formulas.csv.gz`에 있다. 실제 금액/세금/정산 규칙의 근거·승인 상태, 계산 순서와 적용 조건을 관리자와 확정하는 작업은 남아 있다. 실제 규칙을 승인 완료로 간주하거나 가상 수식을 실제 규칙의 대체 계약으로 사용하면 안 된다.

결함 주입 결과: 0 수량 허용 44건, 회사 경계 우회 3건, 불확실 실행 재시도 122건, 금액 절사 270건 실패를 검출하고 모두 자료 인수를 차단했다. 반복 불일치 묶음과 개별 증거는 각 `mutation-*.json.gz` 전체 실행 보고서로 보존한다. 근본 원인이 같다는 수동 판단과 `unique_failures`를 혼동하지 않는다.

## 다음 적용 절차 / 남은 관리자 결정

1. 프로젝트 소유자가 대상 스테이징 SHA·정책/설정 버전·테스트 데이터·격리 실행 이미지/경로·한도를 승인한다.
2. 업무 담당자가 실제 흐름·등급·커버리지·계산식 근거/승인을 검토한다. 어댑터 이름/버전과 독립 오라클을 등록하고 서버 밖의 신뢰된 호스트에서 승인 manifest를 보관한다.
3. 실행기를 등록된 경로에 연결한다. 프로세스 시간 제한/중단, 비밀값 제거, 외부 효과 대조, 증거 출처의 신뢰를 실행기에서 보장한다. 이번 접수 API 자체를 실행 sandbox로 사용하면 안 된다.
4. 접수→실행권→관찰→결과 제출→관리기 GET 회수를 수행한다. 결함 주입·소스 변경·커버리지 삭제가 차단되는지 다시 확인한다.
5. 실제 비운영 서비스 하나에서 UI/저장/권한/실패 복구를 검증한다. 이번 오프라인 컴포넌트 검사만으로 이 조건을 완료 처리하지 않는다.
6. `require_for_task()`로 기존 개발 작업에 사전 승인 계약을 필수 결합한다. 일반 `Store.review`와 3단계 기술 인수 `ThreeTier.decide(accept)`가 같은 트랜잭션에서 계약·후보 소스·현재 통과 증거를 재검증한다. 소유자가 승인 전 필수 결합한 작업에 적용하며 기존 프로젝트 전체에 자동 강제하지 않는다. 실제 merge/deploy는 별도 승인 경로다.

운영 배포, 유료 자원 생성, 실결제, 메시지 전송, 운영 데이터 변경은 수행하지 않았다. 불확실 상태는 통과로 바꾸지 않았다.

## 최종 검사 기록

실행 코드 리비전은 `e3f515e0d88e7ba49c67a35404352bb58939df49`다. 문서/증거 추가 커밋은 새 실행 성공으로 간주하지 않는다. 전체 저장소 회귀는 `python -m unittest discover -s tests -q`로 1,660개 실행(1,659개 통과, 1개 skip, 실패 0)을 확인했다. 인계된 기존 1,652개에 새 검사 8개를 더한 수다. 관리자 회귀 1,356개 실행(1개 skip), 공통 코어 245개 통과, 최종 인수·HTTP·저장소 집중 검사 79개 통과를 확인했다. 집중 검사는 회귀 검사와 중복되므로 합산하지 않는다. 동일 소스·시드로 전체 합성 및 결함 주입 artifact 8개를 두 번 생성하여 바이트 일치를 확인했다. 해시는 `SHA256SUMS`, 등급/흐름별 집계는 `results-by-priority-flow.json`, 검사 범위는 `verification.json`에 있다.

| 검사 묶음 | P0 통과 | P1 통과 | P2 통과 | P3 통과 | 실패·차단·미검증 |
|---|---:|---:|---:|---:|---:|
| 기존 합성 계약 | 3 | 2,715 | 129 | 159 | 각 0 |
| 실제 주문 정규화 코드(오프라인) | 해당 없음 | 288 | 해당 없음 | 해당 없음 | 각 0 |

이 표의 미검증 0은 생성한 계약 시나리오 안의 상태만 뜻한다. 위에서 열거한 실제 서비스 미검증 범위는 그대로 남는다.
