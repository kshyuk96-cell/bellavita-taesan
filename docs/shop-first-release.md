# 벨라비타 첫 운영판 · 출시 준비 현황

2026-11-14 기준. 첫 운영판의 기능 범위를 고정하고 실제 운영 검증 단계로 전환한다. 새 관리자 편의 기능 제안과 추가 개발은 중단한다. 현재 단계는 **핵심 기능 구현·모의 리허설 완료 / 실제 연동·운영 전환 대기**다. 첫 운영판의 직원·고객 알림은 사용자 결정에 따라 **카톡 알림톡 + 샘플 이미지 확인 링크**로 확정했다.

## 목표와 범위

운영자가 승인한 4개 상품과 옵션을 등록하고 행사별 가격 링크를 발급한다. 고객이 상품·문구·보내는 분·설치 정보를 확인해 주문하고, 페이앱 결제·취소를 같은 주문번호에 반영한다. 직원·고객에게 문구 샘플을 전달하고 주문 확인→배송 중→배송 완료를 관리하며 재배포 후에도 기록을 보존한다.

기능 범위 동결 후에도 상품 사진·가격·옵션은 기존 관리자 기능으로 수정할 수 있다. 기존 주문과 이미 발급한 링크의 조건은 보존한다.

기존 초대장·직원 승인 경로를 유지한다. 이미 구현한 관리자 편의 기능은 보존하되 출시 조건을 늘리는 새 기능은 추가하지 않는다. 회원·장바구니, 실제 자동 인쇄·공장 실행·운영 Sheets 쓰기는 첫 출시의 필수 범위로 확대하지 않는다.

```mermaid
flowchart LR
 A[상품·옵션] --> B[행사별 링크·고객 주문]
 B --> C[서버 금액·페이앱 통보]
 C --> D[직원·고객 알림과 샘플]
 D --> E[주문 확인·배송 중·배송 완료]
 E --> F[기록 보존·백업·복구]
```

## 출시 마무리 다섯 단계

| 단계 | 현재 상태 | 완료 기준 |
|---|---|---|
| 1. 범위 확정 | 완료 | 이 문서의 기능·수용 기준으로 고정 |
| 2. 최종 화면 확인 | 기술 검증 완료, 운영자 최종 확인 대기 | 4개 상품의 실제 가격·옵션·이미지·설치 안내·문구를 운영자가 승인 |
| 3. 실제 연동 검증 | 미완료 | 가맹점 승인/취소, 직원·고객 실제 수신, 대상 영수증 실제 결과 대조 |
| 4. 운영 리허설 | 자동 모의 리허설 통과, 직원 실사용 확인 대기 | 담당자가 주문 한 건을 접수부터 배송 또는 취소까지 처리 |
| 5. 운영 전환 | 계획 준비, 미실행 | 운영 데이터/백업 확인 후 별도 배포 요청에 따라 병합·검증 |

진척을 하나의 퍼센트로 합산하지 않는다. 모의 성공, 실제 공급사 성공, 운영자 승인, 운영 배포를 각각 관리한다.

## 현재 실환경 관찰

- 검증 서버 `/healthz`, `/shop`, `/verification`은 HTTP 200, 공개 상품 4개, 기존 모의 주문 3건, SQLite 무결성과 영구 디스크 확인.
- 검증 서버 실행은 `shop_verification.py`이며 실결제·실발송·실발급·운영 쓰기를 강제로 끈다. 이 환경의 설정만으로 실제 운영 계정의 설정 유무나 거래 성공을 판정하지 않는다.
- 검증 환경에서는 알림톡 필수 4항목, 직원 수신자, 상품 과세 구분 4개, 서버 자동 외부 백업 인증이 실연동 준비 완료로 확인되지 않았다. 운영 계정은 이번에 직접 조회하지 않았다.
- 배포가 포함된 관측 구간에서 502 두 건이 집계됐다. 해당 요청의 개별 원인은 확정하지 않았다. 이후 12:52 UTC부터의 별도 관측에서는 5xx 0건, 현재 직접 조회 200, 앱 오류 로그 0건이었다. 트래픽이 적고 p95 자료가 없어 부하 성능 통과로 표시하지 않는다.
- 영구 디스크를 붙인 단일 인스턴스는 무중단 재배포 대상이 아니다. 운영 배포는 짧은 중단을 고려하고, 결과 불명 거래와 통보 재전송을 대조한다.
- 기존 main 서비스는 main 커밋 자동 배포가 켜져 있고 별도 1GB 디스크가 붙어 있다. 실제 `TAESAN_DATA`가 그 디스크 아래인지 이번 읽기 전용 도구로는 확인하지 못했다. 기존 서비스와 설정은 변경하지 않았다.

## 운영자 최종 확인 · 5분 화면 검수

현재 고객 샘플: https://bellavita-shop-verification-v3b4.onrender.com/shop

1. 상품 4개만 전시되는지, 이름·사진·기본 가격·옵션 추가금·배송/설치 안내가 실제 판매 조건과 맞는지 확인한다.
2. 첫 상품의 3호 선택 예시 165,000원과 다른 옵션 조합의 표시 금액을 확인한다. 두 할인 행사 링크는 상품 기본가와 구분한다.
3. 긴 문구와 보내는 분, 주문자 ‘보내시는 분과 같음’, 설치 장소·일시를 모바일에서 확인한다. 화면의 족자 2:3 비율은 실물 mm 확정 근거로 사용하지 않는다. 액자 공개 옵션의 3:2와 실제 출력 규격도 대조한다.
4. 검증 서버에서만 모의 주문을 진행하고 관리자에 동일 주문번호·문구·가격이 남는지 확인한다. 실제 결제 수단을 이 모의 서버에 연결하지 않는다.
5. 알림 전달 방식은 카톡 샘플 링크로 확정됐으며 운영자는 최종 상품 조건을 확인한다. 관리자 매뉴얼은 [shop-admin-manual.md](shop-admin-manual.md)에 있다. 현재 검증 관리자 링크는 별도 발급하며, 카카오의 운영 관리자 진입은 운영 전환 후 확인한다.

## 실제 연동 착수 상태 · 접근 확인

현재 연결은 Render 서비스·배포·로그 조회를 제공하지만 서비스 환경변수 값 조회·서버 셸 실행을 제공하지 않는다. 작업 환경에도 Render CLI와 API 인증이 없어 기존 main 서비스의 실제 저장 경로를 직접 확인하지 못했다. 페이앱·SOLAPI 계정을 직접 조회하는 연결도 없으며 작업 환경의 해당 인증 설정도 확인되지 않았다. 이는 실제 계정 설정이 안 됐다는 판정과 구분한다.

운영자는 첫 운영판의 직원·고객 알림을 **카톡 알림톡 + 샘플 이미지 확인 링크**로 확정했다. 문자 대체 발송은 끈다. 이 결정은 실제 채널·템플릿 승인이나 단말 수신 검증 완료와 구분한다.

저장소 접근이 확보되면 [읽기 전용 점검 도구](../tools/check_shop_storage.py)를 다음과 같이 실행한다.

```sh
python tools/check_shop_storage.py --data "$TAESAN_DATA"
```

이 도구는 명시된 기존 DB를 읽기 전용으로 열어 경로·마운트·무결성·주요 테이블 건수·공개 상품 과세 누락 수만 출력한다. 앱을 시작하거나 DB/상품을 생성·이전하지 않고 고객·주문자 정보나 비밀값을 출력하지 않는다. 없는 테이블은 0건으로 추정하지 않고 null로 표시한다. 운영 승인과 공급사 검증은 판정하지 않는다.

현재 main에는 이 점검 도구가 없을 수 있으므로 실행을 위해 운영 병합·재배포하지 않는다. 승인된 셸 접근에서 검토한 도구 소스를 표준입력 또는 임시 파일로 실행할 수 있다. 실제 데이터 경로가 확인되지 않으면 중지하고 기본 경로로 새 DB를 만들지 않는다. 로컬 독립 복구 DB에서 도구와 비변경 테스트 2개를 통과했으며 운영 서비스에서 실행한 것으로 기록하지 않는다.

## 실제 연동에서 필요한 확인과 결과물

### 페이앱

가맹점 제공 테스트 계정/수단, 허용 금액·취소 범위와 권한을 확인한다. 현재 모의 서버가 아닌 독립 실가맹점 검증 환경에 계정 설정을 등록하고 그 환경의 HTTPS `/invitation-orders/payapp` 통보 주소를 사용한다. 실제 거래가 필요하면 주문금액·결제 수단·취소 계획을 먼저 확정한다.

승인·중복 통보·부분취소·전체취소·늦은 승인·결과 불명 대조를 주문번호와 결제번호로 기록한다. 브라우저 성공 화면만으로 완료 처리하지 않는다. `INVITATION_PAYAPP_USER_ID/LINK_KEY/LINK_VALUE/REQUEST_KEY`의 실제 값은 서비스 비밀 설정에서 관리한다.

### 알림과 샘플

첫 운영판은 사용자 결정에 따라 **직원·고객 모두 카톡 알림톡으로 샘플 이미지 확인 링크를 받는 방식**으로 확정했다. MMS 이미지 첨부는 기존 구현을 보존하되 첫 운영판 선택 채널로 활성화하지 않는다. 문자 대체 발송도 끈다.

선택한 알림톡에는 SOLAPI API 키/시크릿, 카카오 채널 PFID, 승인 템플릿·상태별 변수, 직원 수신번호, 발송 채널 설정이 필요하다. 직원·고객 각각의 실제 단말에서 주문 확인/배송 중/배송 완료/취소 알림과 문구 샘플을 확인한다. 발송사 접수와 실제 수신을 구분한다.

확정 채널의 준비 설정은 `SHOP_MESSAGE_CHANNEL=alimtalk`이다. 실제 발송 검증 전까지 `SHOP_MESSAGES_ENABLED=0`, `SHOP_ALIMTALK_ENABLED=0`을 유지한다. 현재 모의 검증 서버의 강제 비활성 설정은 바꾸지 않는다. 과거 모의 대기열을 실발송 환경으로 옮기지 않는다.

승인 요청용 문구 초안은 다음과 같다. 실제 채널의 허용 변수/버튼과 승인 결과를 대조한 뒤 사용한다.

> [벨라비타] #{상태}
> 주문번호: #{주문번호}
> 상품: #{상품명}
> 입력 문구 샘플 확인: #{샘플링크}
> 주문·배송 확인: #{주문링크}

직원과 고객의 샘플 링크는 주문별 이미지 확인 화면으로 연결한다. 직원의 주문·배송 링크와 고객의 주문 상태 링크는 서로 구분하며, 고객에게 직원 작업 권한을 전달하지 않는다. 발송 결과 불명 시 문자로 대체하거나 같은 알림을 자동 재요청하지 않는다. 이 채널의 기존 모의 테스트 3개(링크/중복/결과 대조, 결과 불명 대체 차단, 고객/직원 권한 분리)를 다시 통과했다. 실제 발송사·단말 검증은 실행하지 않았다.

### 현금영수증

네 상품의 과세/면세와 페이앱·쇼핑몰 중 발급 주체 하나를 확정한다. 모의 리허설의 합성 TG02 설정을 실제 상품에 복사하지 않는다. 대상 결제수단의 실제 발급·취소/부분취소 정정·실패/결과 불명 처리와 중복 발급 방지를 승인번호로 대조한다.

### 외부 백업

수동 암호화 저장·재다운로드·복구 검증은 완료됐고 서버의 무인 자동 업로드 인증은 별도다. 외부 저장소의 서버 인증과 권한을 확인하고 실제 업로드→재다운로드→복구 성공을 확인한다. 복구 키의 별도 보관도 운영자가 확인한다. 상세 설정은 [운영 준비 안내](shop-operational-readiness.md)를 사용한다.

## 운영 전환 순서 · 이번에는 실행하지 않음

1. 위 실제 연동 결과와 운영자 화면/직원 리허설 확인을 모은다. 미확인 항목을 성공으로 간주하지 않는다.
2. main 최신 커밋과 PR #20의 변경·회귀 결과를 다시 대조한다. 현재 확인한 main은 PR의 선조이며 이번 작업은 main을 변경하지 않았다.
3. 운영 서비스에서 `TAESAN_DATA`의 실제 경로·DB·초대장 파일·디스크 마운트·남은 용량을 읽기 전용으로 확인한다. 디스크가 붙어 있다는 사실만으로 데이터 경로를 추정하지 않는다.
4. 필요한 중단 시간과 통보 재전송 절차를 정하고 기존 DB와 초대장/샘플 파일을 백업해 새 경로에서 복구를 검증한다. 경로 이동이 필요하면 원본을 보존하고 이전 전후 건수·해시를 대조한다.
5. 별도 운영 배포 요청에 따라 main 병합·배포를 진행한다. 기존 main 서비스의 커밋 자동 배포를 고려한다. 저장소의 기존 `render.yaml`에는 free 계획이 남아 있어 현재 유료 디스크 서비스와 다르다. 확인 없이 Blueprint를 다시 적용하거나 기존 서비스를 재생성하지 않는다.
6. `agent.py`는 승인 상품을 자동 등록하지 않는다. 운영 DB·백업이 확인된 뒤 `python seed_shop_catalog.py --data /확인된/운영/데이터경로`로 네 상품을 INSERT OR IGNORE 등록하고 실제 4개 전시를 확인한다. 기존 상품 편집을 덮어쓰지 않는 동작을 확인한다.
7. 새 쇼핑몰 결제·알림·영수증은 승인된 범위에 맞춰 단계별로 활성화한다. 기존 초대장 경로·권한·기존 서비스 쓰기 설정을 임의로 바꾸지 않는다. 모의 주문 DB/대기열을 운영에 복사하지 않는다.
8. 배포 완료와 `/healthz`만 보지 않고 실제 상품/관리자/기존 고객 링크를 확인한다. 주문 한 건을 대조하고 오류·미확인 거래·알림·영수증을 점검한다.
9. 코드 롤백은 데이터·외부 결제·발송을 되돌리지 않는다. 이전 코드와 현재 DB의 호환성을 확인하고 원본을 덮어쓰지 않는 복구 방식을 사용한다.

기존 `render.shop-verification.yaml`은 모의 검증용이다. 실제 운영 결제 환경으로 그대로 전환하거나 운영 키를 복사하지 않는다.
