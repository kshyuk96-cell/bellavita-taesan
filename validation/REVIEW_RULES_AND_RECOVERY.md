# Location, multiple orders, title choices and recovery

- Changes to a previously known venue or address require both current venue and current address. Lifecycle edits and assistance supplements share the same guard. This prevents retaining an old venue/address counterpart; it is not geocoding or proof that the newly supplied pair matches.
- Explicit `[주문1]`, `[주문2]` boundaries produce separate preview sections. Common unlabeled prefixes, repeated numbers and empty sections require clarification. Each order must then be submitted separately. Free-form multi-order inference and atomic multi-order submission are not claimed.
- A multiline sender remains an ordered set by default. Explicit `[모두 인쇄]` preserves all following lines; `[선택: 2]` selects the second candidate. Unresolved alternatives such as 'A 또는 B', malformed directives and out-of-range selections are held before invitation requests. This mechanism does not guess whether a real customer's historical titles are a set.
- Recovery tests exercise a sheet batch applied before a timeout using the real Ledger.save method with a fake sheet transport: retry finds the stable marker and does not post another row. Queue tests simulate remote completion before acknowledgment, and a notification failure after saving; local rollback preserves update state and retries the same marker. No live network calls are used. Multi-process writer coordination and arbitrary hard-crash timing remain unverified.
